Identifying your unit

For: someone holding a handheld who does not know which model or chip it is, or which device tree it needs.

sndstation picks what to run by the unit's chip, not by the name on the box. A shop names the model, and two units sold under one name can hold different boards. Find the family first, then, for an RK3326 unit, find the exact board. RK3326 takes most of this page, because it is the hard case.

Which family

Family Sold as
RK3326 the RG351 series, R33S, R36S and its clones, R40XX, RGB10, K36, XU10
RK3566 the RG353 series, RGB30, RK2023, X55
H700 the RG35XX series, RG40XX, RG34XX, RG28XX, RGcubeXX
A133 TrimUI Smart Pro, Brick, Brick Pro

Supported hardware lists the private-beta units and the chip in each, and Peripherals says what each family takes over USB.

The label printed on the circuit board is a good second check. On an R36S it is six screws away, with the battery unplugged first. The label names the board, not the screen panel, and it can be faked (see When it is not an RK3326).

What you have to get right, by family

No card works out which board it is in. Every card carries all of its family's device trees in dtbs/ and their overlays in overlays/, and one file on the card's FAT partition names which to use. What you have to find out before you set that file differs by family:

RK3326 H700
What differs between units the board: panel, joypad, audio, keys. One model name can cover many boards the RAM, DDR3 or DDR4. The model name fixes the board
What you choose a device tree, plus any overlays it needs the image for the unit's RAM, then the device tree for the model
Where it is set config.txt: fdtfile= and overlays= extlinux/extlinux.conf: FDT and FDTOVERLAYS

RK3566 sits between them: pick the device tree for the model in extlinux/extlinux.conf, like H700, and a few boards (X55, X35S, RG-DS) take a different bootloader. The A133 units have one board each, so there is nothing to pick.

Device trees and overlays

A device tree (.dtb) describes a whole board, and a unit boots from exactly one. An overlay (.dtbo) is a small patch applied on top of that device tree: it changes one part, such as the panel, and leaves the rest as it was. An overlay never replaces the device tree. The right device tree with a missing overlay still leaves that one part wrong.

Overlays are applied in the order they are listed, after the device tree. RK3326 is the family that needs them most. Two you will meet there:

  • mipi-panel.dtbo, for a unit whose screen is not the one its device tree expects.
  • The USB OTG overlay. The RK3326 device trees taken from stock cards, all but the GKD Pixel 2's, leave the OTG port switched off. Without the overlay, USB networking binds but nothing reaches the cable.

RK3326: find the device tree before you flash

Why RK3326 is different

Hardkernel's ODROID-GO Advance was the first of these. Anbernic cloned it, then Powkiddy, then many more shops, and each one used its own parts: a different panel, joypad, audio chip, or key wiring. By one count there are more than 70 named RK3326 variants, not counting the R36S clones, and new names turn up every week. "R36S" alone can mean dozens of boards, each with its own device tree. The handhelds.wiki RK3326 list and its R36S clones page track them.

The device tree (a .dtb file) tells the kernel which parts the board has. With the wrong one, the screen stays dark, the buttons are wrong, or there is no sound.

The RK3326 image boots on the first try only on an Anbernic RG351V. On any other RK3326 unit, find its device tree first.

Find it from the original card

  1. Keep the card the unit came with. Do not flash it or wipe it. It holds the stock device tree, and it is the only proof of which board you have.
  2. Copy the .dtb files off it. Put the card in a computer and look for files ending in .dtb on its partitions. A card can hold several. Only one is loaded, and which one can depend on the card's start-up scripts, so copy them all.
  3. Upload them to DTB Detective. It reads the panel, joypad, audio, and keys out of a device tree and shows the closest known device, with the evidence. It names the device tree to use under ROCKNIX and sndstation, and the overlays to apply on top of it, if any. Treat a match as a strong hint, not a verdict. The site keeps what you upload.
  4. Set both on the sndstation card. Before the first boot, open config.txt on the card's FAT partition. Name the device tree on the fdtfile= line, and any overlays on the overlays= line, in the order to apply them:

fdtfile=rk3326-gameconsole-r36s.dtb overlays=mipi-panel.dtbo

Both must be files the card already holds, in dtbs/ and overlays/. To move the card to another RK3326 board, edit these two lines; there is nothing to copy. 5. Put the result in your report. Name the device tree and every overlay in the hardware report for the unit.

DTB Detective comes from the ROCKNIX community, whose work on these boards made most of this possible.

When it is not an RK3326 at all

Some cheap "R36S" units are not RK3326 inside, even when the chip says so. The best-known is the GA36 fake. Its board is marked GA36-MB V1.0-20250730, and its chip is marked RK3326, but it is an Allwinner A33: a 32-bit chip that sndstation does not run on. The signs:

  • The stock card runs EmuELEC 4.7 on a Linux 3.4 kernel.
  • The card has an Android-style layout, with a raw U-Boot partition and a boot image, and no .dtb file at all.
  • DTB Detective has nothing to read, since there is no device tree.

phaseloop's GA36 notes document the board, its partitions, and a recovery image. The unit cannot boot without its original card, so keep that card.

A GA36 is a dead end for sndstation. Its battery and screen still make good spares. For something to run sndstation on today, a Raspberry Pi with Raspberry Pi OS Lite (trixie) takes the .deb as it is and runs full screen (Installing on a handheld).

Buying an RK3326 unit

An R36S is a lottery: the name says little about the board inside. Any other RK3326 model is a better bet. The maintainers' current pick is the K36: its two USB ports and headphone jack are on the top edge, out of your hands' way, and it has one microSD slot. It is not one of the beta's slots. The device guide ranks the rest.

H700: match the RAM, then the model

An H700 model has one board, so its name tells you the device tree. The table in Supported hardware names each one. A model sold with a second screen panel has a second device tree, such as sun50i-h700-anbernic-rg35xx-h-rev6-panel.dtb: on H700 a panel revision is its own device tree, not an overlay.

What varies is the RAM. Units of one model ship with DDR3 or DDR4. The device tree is the same for both, but the bootloader that starts the RAM is not. An H700 image is built for one or the other and says so in its name, as in sndstation-H700-DDR4-….img.xz. The wrong one hangs before the kernel starts, with nothing on screen.

To tell which you have, read the vdd-dram regulator on a running unit, for example under the stock firmware:

grep . /sys/class/regulator/regulator.*/name     # find vdd-dram
cat /sys/class/regulator/regulator.N/microvolts  # N from the line above

1100000 is DDR4, which most units have. 1200000 is DDR3. A DDR3 card already applies its ddr3 overlay first; list any other overlay after it.

Then set the model's device tree on the FDT line of extlinux/extlinux.conf, and any overlays on the FDTOVERLAYS line, separated by spaces:

FDT /dtbs/sun50i-h700-anbernic-rg40xx-h.dtb
FDTOVERLAYS /overlays/my-panel.dtbo

Once sndstation runs

The launcher's ABOUT page shows the unit's own identity, read from the chip: the SOC ID row. Two units of one model get different ids. See Which unit this is.
