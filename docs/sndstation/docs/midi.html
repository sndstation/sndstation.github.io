MIDI devices

<sndstation/midi.h> gives an app the unit's MIDI devices, in and out. Every message crosses the API as UMP, the Universal MIDI Packet of MIDI 2.0:

  • a MIDI 1.0 channel message is one 32-bit word (message type 2), sysex is a run of two-word packets (type 3), so MIDI 1.0 gear loses nothing;
  • a MIDI 2.0 device's channel voice messages (type 4: 16-bit velocity, 32-bit controllers) arrive at full resolution where the unit can carry them.

An app that wants bytes asks UmpToBytes, which also scales MIDI 2.0 down by the specification's rules. CLAP carries both: CLAP_EVENT_MIDI2 is one UMP, for a plugin whose note port prefers the MIDI 2.0 dialect.

The usual app

struct Synth : sndstation::midi::Sink {
    void received(const sndstation::midi::Port&, const uint32_t* ump, size_t words,
                  uint64_t timeNs) override { /* queue it for the audio thread */ }
};

Synth synth;
sndstation::midi::listen(&synth);   // the unit's inputs, now and as plugged in
...
sndstation::midi::stop();

received() runs on the SDK's MIDI thread, one packet per call: neither the audio thread nor the UI thread. Copy the packet somewhere lock-free and return.

To pair a BLE-MIDI keyboard or pad, the launcher's Settings → MIDI → MIDI controllers scans for BLE-MIDI gear over Bluetooth; it is the same screen as Settings → Network → Bluetooth → MIDI controllers. Once connected, BlueZ gives the device an ALSA sequencer port, which midi::open() picks up as it appears, exactly as it would a USB keyboard.

To see what a device sends, the launcher's Settings → MIDI → MIDI monitor lists every port and logs every input, decoded and in hex (launcher.md). Its source, launcher/midimon.cpp, is also a worked example of a Sink that hands packets to a UI thread through a lock-free ring.

The unit's choice of ports

system.json:

"midi": { "in": ["*"], "out": [] }

Port names or ids, or "*" for every port there is (the sequencer's own loopback, Midi Through, excepted). listen() opens every input named, and any that is plugged in later. outputs() lists the outputs named, for apps that send. An app may also list ports() and open() what it likes.

Tiers

The handhelds' kernels differ in what they build. Across ROCKNIX's device families today, one has the sequencer with UMP and USB MIDI 2.0, several have the sequencer without UMP, and several have no sequencer at all, only the raw MIDI devices. So the backend decides when it starts, from what it finds, never from the build alone, and logs the tier it is on:

Tier When What you get
sequencer (UMP) the kernel's sequencer has UMP, and alsa-lib is 1.2.10 or later MIDI 2.0 gear native; MIDI 1.0 gear converted by the kernel; ports shared with other programs
sequencer (legacy) a sequencer without UMP, or an older alsa-lib MIDI 1.0, converted here; ports shared
raw MIDI no sequencer MIDI 1.0, converted here; /dev/snd/midiC*D* directly, so one program per device
none no MIDI, or another OS an empty port list

alsa-lib's UMP calls are looked up at run time, not linked by name, so one binary built against a new alsa-lib still starts on a unit with an old one, on the legacy tier. A build against headers older than 1.2.10 leaves the UMP tier out.

SNDSTATION_MIDI_TIER=legacy or =raw starts lower down, to try a tier on a unit that has a better one.

Timestamps are CLOCK_MONOTONIC, taken as each packet is read.

macOS and Windows

No devices yet: the build there uses a backend with an empty port list, and the UMP helpers work as everywhere. Both platforms' current APIs are UMP-native (CoreMIDI's MIDIEventList, Windows MIDI Services), so each is a backend of the same shape when it is wanted.
