Software packages

SETTINGS → Software packages is everything the unit installs, through apt:
UPDATES the unit's updates, the system's, sndstation's and the vendors': apt-get update, then what apt upgrade does, shown whole (below). Its row names the sources they come from: Includes: Debian, Debian-Security, sndstation, Sound Works.
SNDSTATION the sndstation source's packages: apps, plugins, sounds, skins. Its row says how many are installed, how many more are available, and UPDATES AVAILABLE when one of those installed has a newer version. A gets or updates one; Y removes one.
VENDORS one row, however many vendors the unit has: their names, how many of their packages are installed and how many more are available, UPDATES AVAILABLE when one of them has a newer version of something installed, and in red any that did not answer. A opens their list, a page of its own: each vendor, with a tile of its own color, its row as sndstation's, and in red with apt's reason when it did not answer. There, A lists a vendor's packages: demos and free ones. Nothing is asked: a vendor is trusted by being in the sndstation-vendors package (below). Y removes a vendor from the unit, after a card that says what stays; its row then says removed, and A on it adds it back. B on a vendor's packages goes back to the list. A list longer than the page follows the selection, and says which of how many it is on.
FROM FILES Install a .deb file: a full version, bought from a vendor, from a card or a stick; shown first, installed on A. And the packages installed that way, to remove. A .deb opened in STORAGE's files comes here too.

Opening the page asks every source before it shows a count: apt-get update for every source apt has, whether each vendor whose source is not written yet answers (ping, below), then what each source has against what is installed, and what an upgrade would take. Until then the page is grey and only B works, with how many sources have answered and for how long. X (rescan all) asks again. That look is the UPDATES page's too, so opening it does not ask every source a second time.

Offline, nothing is asked. Whether the unit is online is NETWORK's answer (Wi-Fi joined, or a wired link up with an address; USB to a PC is not one), read every 30 seconds. Offline, the page shows what is installed, from the unit's own lists, and is not gray: Y removes a package. Getting, updating, Get all and setting up a vendor whose source is not written yet say "Offline: connect in NETWORK first". The background check and the UPDATES page's own check are skipped too.

Not known yet is not online. Just after the launcher starts, NETWORK has not read the unit's status yet. Until it has, the page is as it is offline: what is installed, removable, and nothing asked. Once NETWORK says the unit is online, the sources are asked, and they are too when the unit comes online while the page is open, without X. The background check waits for NETWORK to say the unit is online.

"Up to date" only after every source answered. SETTINGS' row, the UPDATES row here and the UPDATES page say up to date only when the last check reached every source apt has. Otherwise they say how many updates the unit's lists know of ("· offline" after it while offline), offline, or how many sources did not answer.

In a source's list, an installed package is in the style's ok color and one not installed is gray; one with an update shows both versions, the installed one and then its source's, in note (docs/sdk-style.md, state colors). A gets a package or updates that one alone; Y removes an installed one, with an update pending or not. A never removes.

Leaving the page after anything was installed, removed or upgraded walks the plugin folders, as the launcher does at start: a CLAP plugin a package brought is checked and reported, and one it took is gone from PLUGINS, and from what every app reads. APPS is read again too, as it is the moment each install ends.

Every update is listed with where it comes from, from which version to which, and how big it is; while anything installs, apt's own progress and log are on screen. Nothing is installed unless someone asks.

Where packages come from

  • Debian (or the unit's base system): its updates only, in UPDATES.
  • sndstation, https://sndstation.s3.us-west-1.amazonaws.com, suite stable: the platform's own updates, and its extra packages, free. The sndstation package ships the source (/etc/apt/sources.list.d/sndstation.sources, a conffile) and the key it is signed with (/usr/share/keyrings/sndstation-archive-keyring.asc); a package built without that key (packaging/sndstation-archive-keyring.asc) ships no source at all, as an unsigned one would fail every check.
  • Vendors: instrument and effect makers, each with its own signed source, which carries demos and free products only. A vendor in the sndstation-vendors package is trusted: its source is written when that package is installed, and the unit does not ask.
  • Files: a full, registered product is never in a source. It is a .deb the buyer gets from the vendor, and installs from wherever they put it.

Vendors

A unit's vendors are files in /usr/share/sndstation/vendors, put there by a package (the platform names none itself):

# /usr/share/sndstation/vendors/soundworks.vendor
Name: Sound Works
About: Instruments and effects: demos and free ones
URIs: https://apt.soundworks.example/debian
Suites: stable
Components: main

A flat repository (one directory with no dists/, as on a GitHub release) names the suite ./ and no Components.

Beside it is the public key its source is signed with, soundworks.asc (armored) or soundworks.gpg. Turning one on (sndstation-updates vendor-on soundworks) writes its source, /etc/apt/sources.list.d/sndstation-vendor-soundworks.sources, signed by that key, and pins it below the system's (/etc/apt/preferences.d/sndstation-vendor-soundworks.pref, priority 100, by its host):

  • a package only the vendor has installs and updates from it as from any source;
  • a package the system or sndstation also has never comes from it, at any version: a vendor's source adds packages, it never replaces one.

vendor-off removes both files, and notes the vendor's id in /etc/sndstation/vendors-off. What the vendor installed stays, and gets no more updates; removing it is the package list's.

Being in the package is what makes a vendor trusted. The project vets a vendor before its definition goes in, and the package's install script turns on every vendor it holds. The page has no trust step. What this means for a unit:

  • every vendor's source is asked on each check for updates, so a vendor whose server is down shows as did not answer, in red, until it is back;
  • nothing of a vendor's is installed until a user gets it from its list: a source adds packages to choose from, and updates what was chosen;
  • the pin (above) still holds: a vendor never replaces a package of the system's or sndstation's.

Removing a vendor is the owner's. Y on a vendor's row asks first, then runs vendor-off: its packages are no longer listed or updated, what it installed stays, and its server is no longer asked, not even whether it answers. Y works on a vendor that is not set up yet too, so the package does not turn it on later. The vendor stays removed through every upgrade of sndstation-vendors, until A on its row (vendor-on) adds it back, with no question. Removing works offline; adding back fetches the vendor's lists, so it waits for a network.

The definitions reach a unit with their package, sndstation-vendors, and so do their changes, with nobody editing a file. The platform builds it: packaging/make-vendors-deb.sh, which packaging/make-deb.sh runs, from packaging/vendors/ (its README says what a definition holds) and from any directory a build passes with --vendors DIR, for vendors an app, an image or a distribution offers that the platform does not. An id defined twice stops the build; a vendor with no source or no key yet is left out, and said.

  • its version moves with the vendors: the platform's revision, or the last change to a vendors directory when that is later, so apt takes a new definition (a vendor's beta) as an upgrade;
  • installing or upgrading it writes the source of every vendor it holds from the definition it brings (its postinst runs sndstation-updates vendor-on ID for each), and removes the source of a vendor it no longer holds, whose key went with its definition, when the helper wrote that source. A file under that name that someone wrote by hand, for a vendor the package never held, is left alone. A vendor the owner removed (its id is in /etc/sndstation/vendors-off) is left removed. A source edited by hand is replaced then, and only then;
  • removing it removes the source and pin of every vendor it held (its postrm), and nothing it did not write. What the vendors installed stays, and so does the list of vendors the owner removed, unless the package is purged;
  • a unit whose sndstation-vendors is 0.16.1 or earlier has sources only for the vendors that were trusted on it. There, A on a vendor's row writes its source, asking nothing, and then lists its packages; its row says not set up yet until then;
  • a source the package wrote during an upgrade has no lists yet. Back from the UPDATES page, the page sees a vendor that is on and was not at its last look, and asks every source again before it shows a count.

Packages, for vendors and for sndstation

Everything the sndstation source and each vendor's has is listed, in every component its source file names (a vendor's beta with its main), apart from the platform itself (sndstation, sndstation-vendors), which updates with the system. A package can say what it is, in a field of its own, which the page shows:

XB-Sndstation-Kind: clap-plugin       (in debian/control; app, clap-plugin, sounds or skin)

which is Sndstation-Kind: clap-plugin in the .deb and in the source's index; one without it is listed as a package. Installing one through the page installs the version its source has (apt-get install NAME=VERSION), never the system's package of the same name, and removing one never takes a package of the system's or the platform itself with it. A .deb file is installed through the page only with the field (below).

Get all: START on a source's list gets every package of it not installed yet (a demo whose full version is installed is not one), after one card that names them and what they download. They install one after the other, each its own helper call, checked against its source as one installed alone is; the first that fails stops it there, and the page says which and how many were got before it.

One install after another, at once: after every install the page reads what updates are pending again, from apt's state with no lock, and an install started meanwhile runs beside it rather than waiting; the list is read once more after it. Only a check of the sources, an upgrade or a repair holds an install back, and the page says so.

A demo and its full version are two packages, so that an update of the demo can never take the full one's place:

in the vendor's source as a file, for the buyer
name soundworks-piano soundworks-piano-full
control Sndstation-Kind: clap-plugin Sndstation-Kind: clap-plugin, Provides: soundworks-piano, Conflicts: soundworks-piano, Replaces: soundworks-piano

Installing the full one removes the demo (it conflicts with it, and replaces its files). Its Provides keeps everything that depended on the demo satisfied, and the page shows the demo as full version installed, with nothing to get. The full version's own updates come as new files, from the vendor.

Removing one never takes anything of the system's with it: the helper refuses when apt would also remove a package that is not one of the platform's, and says which. A package's dependencies stay installed after it is removed (apt autoremove, from a shell, clears them).

A .deb file

Install a .deb file opens the file browser on .deb files. Picking one shows what it is before anything installs (dpkg-deb -f): its name, version, kind, maker, what it replaces, its size, what it needs, and its description; and, when it is already installed, which version. Then:

  • refused: not one of the platform's (no Sndstation-Kind), or built for another architecture;
  • otherwise A installs it, with apt-get install /path/to/file.deb, so what it needs comes from the sources.

A package's scripts run as root, like the system's own: the card says so, and says to install only a file from a vendor you trust.

Publishing a source

tools/apt-repo.sh, on the publisher's own machine (the signing key stays there; nothing publishes from CI):

export REPO_KEY=you@example.org         # the gpg key that signs it
tools/apt-repo.sh add  ~/apt/sndstation dist/*.deb
tools/apt-repo.sh upload ~/apt/sndstation s3://sndstation
tools/apt-repo.sh key  ~/apt/sndstation > packaging/sndstation-archive-keyring.asc

add puts packages in the pool (a version is never replaced, only added) and writes and signs the index (InRelease, Release.gpg) for arm64, armhf and amd64; upload copies the pool, then the index, with the index never cached. REPO_LABEL (default sndstation) is the label UPDATES groups by. A vendor runs the same with its own key, label and bucket.

On S3, a unit reads the source over plain HTTPS, so dists/* and pool/* must be readable by anyone. A new bucket blocks that (Block public access): turn off the two settings about bucket policies (the ACL ones can stay on), then give it a policy that allows reading those two folders and nothing else:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AptRead",
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": ["arn:aws:s3:::sndstation/dists/*", "arn:aws:s3:::sndstation/pool/*"]
  }]
}

curl -I https://sndstation.s3.us-west-1.amazonaws.com/dists/stable/InRelease then answers 200 (or 404 before the first upload), not 403.

On GitHub, a source can be served from GitHub Pages the same way (the directory apt-repo.sh writes, pushed to the Pages branch). A release's assets cannot: apt needs the dists/ and pool/ paths as they are.

The updates

How others do it, and why this follows the command line

What it shows
Ubuntu (Software Updater) a total and an Install button; packages, versions and changelogs behind "Details". Security updates also install in the background by themselves (unattended-upgrades), and some updates are phased, reaching a unit days after others. The least shown.
Debian desktops (GNOME Software, KDE Discover) one "OS updates" block, downloaded in the background and installed on the next restart. Synaptic and apt for the detail.
Linux Mint (Update Manager) every package: its type (security, kernel), old and new version, size, source, description and changelog; packages can be ignored for good; a snapshot is suggested first; nothing automatic unless asked. The most shown.
Raspberry Pi OS a list of packages from a panel icon, then an install.
Handheld images often their own update scripts, and a warning against apt upgrade: it can replace the kernel, the device tree and the GPU's blobs the image depends on.

This page takes Mint's openness on the command line's own path: it is apt-get underneath, with nothing in between that decides on the user's behalf. Its safeguards are the handheld's (below), not hidden choices.

The page
the list the updates, grouped by where they come from (below), each with its versions, size, one-line description and tags: security, new (another update needs it), held, restart. The header says when it was checked and how many sources answered. A: a package; START: install; Y: hold or release it; X: check again; SELECT: the sources.
a package its versions, source, sizes, what its tags mean, and its changelog (apt-get changelog, fetched from its source).
sources each apt source and whether the last check reached it, apt's warnings, and its whole output.
confirm how many packages, what they fetch, from which sources; what stays (held, kept back); Y to take the kept-back ones too, which is a full upgrade and names everything it would remove. Refused on a battery under 30% that is not charging.
installing one bar (downloading its first half, installing its second), the step at hand ("Unpacking openssl"), and as many of apt's latest lines as the screen has room for; Y shows apt's log whole. It cannot be left or stopped: dpkg cut off halfway is how a system stops starting.
done what it came to: a restart needed, a configuration file someone changed whose new version was set aside, a package dpkg could not finish (A repairs it), the log.

Groups

  1. Security: anything from a -security suite or a source labeled so.
  2. Each supplemental source, under its own name, in the order config/updates.json gives (sources): sndstation's, an instrument maker's, a trusted developer's.
  3. Any other source, by the label apt gives it.
  4. System: the base system's sources (system in updates.json).
  5. Kept back: what apt-get upgrade leaves, because it needs a package added or removed (a full upgrade takes it), or because it is held.

A source is named by the Label of its Release file, as apt-get -s upgrade prints it before the colon (Debian-Security:12/stable-security).

On the system side

/usr/lib/sndstation/sndstation-updates (tools/sndstation-updates), run through sudo -n by the same sudo rule as Network's and Storage's:

Verb Does As
refresh apt-get update, each source and how it went, and what each that answered calls itself (its Release file's Label, else Origin) root
list apt-get -s upgrade --with-new-pkgs and -s dist-upgrade (simulations), apt-mark showhold, apt-cache show for sizes and descriptions the user
upgrade [full] apt-get upgrade --with-new-pkgs (what apt upgrade does: may install new packages, never removes one), or with full apt-get dist-upgrade root
repair dpkg --configure -a, then apt-get -f install root
changelog PKG apt-get changelog PKG the user
hold PKG, unhold PKG apt-mark hold/unhold root
holds-default holds the kernel, the device tree and the boot loader, once root
available the sndstation source and each vendor (on, off, or removed by the owner), and every package of those that are on, in every component (read from apt's lists), each with its kind (Sndstation-Kind, or none), its version, the one installed, and the installed package standing in for it (a full version's Provides); then those installed from files the user
install PKG, remove PKG apt-get install NAME=VERSION of a package one of those sources has, at its version there, or of one with a Sndstation-Kind; apt-get remove of one of those, never taking the system's or the platform with it root
inspect FILE dpkg-deb -f on a .deb: its fields, and whether it may be installed the user
install-file FILE apt-get install FILE, when it is one of the platform's root
vendor-on ID, vendor-off ID write a vendor's source, pinned below the system's, or remove it. The sndstation-vendors package runs vendor-on for every vendor it holds; the page runs it for one whose source is not written yet, or to add one back. vendor-off first notes the id in /etc/sndstation/vendors-off, so the package leaves that vendor removed, and vendor-on takes it out again; it refuses an id that has neither a definition nor a source root
ping whether each vendor whose source is not written yet answers: its InRelease (else Release) fetched with apt-helper download-file and thrown away, with the same 10-second limit; refresh asks the others, and one the owner removed is not asked at all the user

A check says what it is doing while it runs, on the page and on the launcher's console: which step (holding the kernel, contacting the sources, reading what is installable), for how long, and each source as it answers. A source that does not answer gives up after 10 seconds, not retried (Acquire::http(s)::Timeout, Acquire::Retries), rather than apt's minutes: the next check tries it again. On the console:

updates: refresh (as root)
updates:   ok   http://deb.debian.org/debian trixie
updates:   FAIL https://apt.example.com stable
updates: refresh: exit 4 in 11.3 s

It answers in lines (updates 1, then tab-separated records and key=value), so it can be run from a shell: /usr/lib/sndstation/sndstation-updates list. An install reports apt's progress through APT::Status-Fd as it comes, one progress record a step, and apt's log as log records; the page reads both live.

Installing never asks a question, which on a handheld would hang it: DEBIAN_FRONTEND=noninteractive, and for a configuration file someone changed, --force-confdef --force-confold: theirs is kept and the package's new version is set aside as .dpkg-dist, which the page names.

Nothing is installed for being recommended: every apt-get it runs has APT::Install-Recommends=false, list's simulations too. A package's Recommends are mostly a desktop's (a file dialog's zenity, and the GTK under it); what a unit needs is a Depends.

Security: what the launcher passes in is a package name or a vendor's id, checked against Debian's rules for a name before it reaches any command, or a .deb file's whole path, which dpkg-deb must read as a package that says it is one of the platform's. Installing a file is installing its scripts as root, which is the unit's owner's call: the sudo rule is a handheld's, whose user is its owner. Under sudo the environment is reset, so its test override is not honored there.

What is held, and why

The first check holds the installed packages matching linux-image-*, linux-dtb-*, linux-u-boot-* and u-boot*, once (a mark in /var/lib/sndstation), so a release later is not undone. On these units the kernel and device tree carry the audio routing and the display; a new one from the base system can lose either. A unit's own list, one glob a line, can be put at /etc/sndstation/update-holds. Holds are apt's own (apt-mark), so apt upgrade from a shell keeps them too. Y releases one.

The background check

While the launcher is on its own pages (nothing playing, no game), it checks at most every check_hours (24): apt-get update, then the list. SETTINGS then says "6 updates, 2 security". What it found is kept in ~/.config/sndstation/updates-state.json, whether every source answered included, so the next start says it without checking again. Offline, it does not check.

What is pending follows what is installed, without the network: the list (apt-get -s upgrade, from the lists apt already has) is read again after anything installed or removed here, at the first idle moment of each run, and whenever dpkg's database (/var/lib/dpkg/status) changes, an apt upgrade at a shell included. An update installed any way stops being offered at once, rather than at the next check. A check that fails (offline) is tried again after an hour. Opening the page checks, unless this run checked within the hour. check_hours: 0 checks only when the page is opened.

Supplemental sources

The way Debian adds a source, unchanged: /etc/apt/sources.list.d/<name>.sources, with Signed-By: naming its key. sndstation's is shipped by its package; a vendor's is written when its package is installed (above). Each one's updates are named by the label its Release file gives, or by the name updates.json gives that label.

Not here

  • Installing anything unasked, security updates included. A unit mid-performance must not change under its player.
  • Restarting. The page says when an update needs one.
  • Phased updates: the page shows what apt would install, phasing and all; a phased update is not listed until apt offers it.
  • Snapshots before an install (as Mint suggests): most units' file systems cannot take one.

Development

sndstation --fake-updates runs the page on made-up updates (a security update, a supplemental source's, a new package, a held kernel, one that only a full upgrade takes), installed slowly enough to watch; and on made-up packages: the sndstation source's, a vendor with its own, one whose source is not written and does not answer, a full version installed from a file, and .deb files (a path ending in -full.deb is one to install, any other is refused). The shots (--shots, 21h–21u) use it. The tests: tests/test_updates.sh runs the helper against stub apt-get, apt-cache, apt-mark, dpkg, dpkg-query and dpkg-deb, over a fake root with apt's lists and a vendor's files; tests/test_updates.cpp reads its output and drives both pages on the fake.
