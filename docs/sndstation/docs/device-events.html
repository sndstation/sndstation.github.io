Device events

<sndstation/deviceevents.h> reports what the unit's body says about itself: a clamshell's lid, the headphone and line-out sockets, a tablet-mode or rotate-lock switch, and an accelerometer or gyro if it has one. SDL's gamepad API never sees any of it, so the SDK reads it from the kernel directly.

It uses no SDL and no threads, and it never grabs a device. The app calls poll() once a frame from its own loop, and logind and everything else watching the same nodes keep seeing them.

The usual app

sndstation::DeviceEvents dev;
dev.open();                                // /dev/input, and the hallkey door if profiled
if (dev.has(sndstation::Switch::Lid)) { /* offer the LID input */ }

// once a frame
for (const sndstation::DeviceEvent& e : dev.poll()) {
    if (e.sw == sndstation::Switch::Lid)
        lidClosed(e.on);                   // on = closed
}

poll() doesn't block. It drains every node, then returns each switch whose state differs from the last call. A switch that flips and flips back within one call is no change: the app only learns where it ended up. on(Switch) is the state now. A switch carried by two nodes counts as on while either holds it. timestamp_ns is CLOCK_MONOTONIC, which does not advance across a system suspend.

The open itself is not news: poll() reports changes from then on. A node that arrives later by hotplug is news, and its switches that are on are reported.

Switch's values are the kernel's own SW_* codes, so the mapping is a cast. switchName() gives "lid", "headphones" and so on for logs.

Where a switch can come from

Every door that was tried is kept in scanned(), the way the audio socket's scan is (SocketSource). A unit that reports nothing can still say where it looked.

kind where what it said
evdev /dev/input/event3 lid, headphones (on: headphones), no switches, an errno
hotplug /dev/input watching for nodes coming and going (inotify), or why not
hallkey a sysfs path reads 1, closed reads 0, unreadable, not configured

evdev

Every /dev/input/event* that advertises any EV_SW bit is kept open. Nodes are found by capability, never by number, since the numbers move with probe order, and are scanned in event-number order, so the report is repeatable.

  • Initial state comes from EVIOCGSW, not from waiting for an event: a switch that nobody is moving emits nothing.
  • SYN_DROPPED means the kernel's buffer overflowed. As the kernel documents, everything up to the next SYN_REPORT is skipped, and then the state is asked for outright.
  • Permission: /dev/input/event* is root:input 0660 once udev has run, so the user has to be in input. A refused node is a row with Permission denied (is the user in the input group?).

Hotplug

open() starts an inotify watch on the input directory. poll() drains it before reading anything.

  • A new node with switches is opened and added. The watch includes IN_ATTRIB, because udev creates a node root-only and opens it up a moment later. A first refusal is followed by a second try that works.
  • A removed node, or one whose read fails with ENODEV, is dropped, and any switch it was holding on reports off.

Both are recorded in scanned(), one row per node saying what happened last, so a dock that comes and goes doesn't grow the list. Units with only built-in switches behave the same as with a single scan at open().

hallkey: profiled, never guessed

The Allwinner BSP kernels that the stock Anbernic images ship report the RG35XX SP's lid as a hallkey attribute under /sys/class/power_supply, not through evdev. The door's code lives here. Which node to read and which value means closed come from the unit's entry in the platform's deviceevents.json, never from code:

"Anbernic RG35XX SP": {
  "hallkey": { "node": "axp2202-battery", "closed": 0 }
}

The file is keyed and merged like leds.json: "*", then the board model, then the unit id, widest first. node is a power_supply node's name or an absolute path. Both fields are needed. A unit with no entry never tries the door, so the polarity is never guessed on hardware nobody has measured, and scanned() lists it as not configured. The file ships empty: the SP on the sndstation rootfs runs a mainline kernel, and its lid is evdev gpio-keys-lid (value 1 = closed), with no hallkey at all.

hallkeyFromProfile() is that lookup through appcfg::platform. hallkeyFor(json, board, unit) is the same thing on a file already read.

Motion: the accelerometer, the gyro, and which edge is up

Motion is the second kind of source. It is read as state, not reported as events: an accelerometer changes every frame, and the app wants the latest reading.

if (dev.hasMotion(sndstation::Motion::Accelerometer)) {
    sndstation::MotionSample a = dev.motion(sndstation::Motion::Accelerometer);
    // a.x, a.y, a.z in m/s^2; dev.motion(Motion::Gyroscope) in rad/s
    if (dev.orientation() != lastOrientation) { /* turned */ }
}

open() scans /sys/bus/iio/devices. Every iio:device* with in_accel_{x,y,z}_raw or in_anglvel_{x,y,z}_raw is a sensor, and every poll() takes one reading per kind, from the first sensor of that kind that reads.

  • Units: each axis is (raw + offset) * scale. The per-axis _x_scale/_x_offset is used before the shared _scale/_offset. The IIO ABI makes this m/s² for accelerometers and rad/s for gyros.
  • The unit's own axes: x to the right, y up the panel, z out of it. The sensor's in_accel_mount_matrix (or mount_matrix) turns its readings into them, so a chip soldered on a quarter turn round reads the same as one that isn't. Lying flat and face up, a unit reads z ≈ +9.8.
  • orientation(): which edge is up (Up, Left, Right, Down), or Flat, worked out from the accelerometer.
  • An edge counts once it is within 35° of vertical, and Flat within 35° of face up or down. Between those, the previous answer stands, so a unit held at 45° doesn't flicker.
  • A reading too weak to show gravity (falling, shaken) changes nothing.
  • orientationOf(x, y, z, previous) is the same rule as a pure function.

Each IIO device is a row in scanned() (kind iio), with its name, scale and mount matrix. A device without motion channels, such as a battery ADC, says no motion channels.

Not yet: nothing drives display.rotate from orientation, and how the RG Rotate reports its rotation hasn't been looked at. The test hook is addIio(dir), which the test points at a fake IIO tree.

The lid policy: what closing the lid does

What a shut lid does is the platform's setting, shared by every app on the unit, in system.json:

"system": { "lid": "suspend" }
value the unit the app
"suspend" (shipped) sleeps when the lid shuts and wakes when it opens. This is logind's own default. gets the Lid event a moment before the freeze. On the SP that window was about 3.6 s, measured, so it should only get ready (stop the audio, darken the lights).
"keep-playing" stays awake keeps playing, and may blank the panel
"off" stays awake takes no notice of the lid

Any other value reads as "suspend", with a warning on stderr, so a typo can't leave a unit awake in a bag.

An app never suspends the unit itself. logind does the suspending, and the platform tells logind what to do:

  1. At boot, sndstation-lid.service runs before systemd-logind. It's a oneshot, linked into /etc/systemd/system on a handheld by the package.
  2. It runs sndstation-lid-apply. That runs sndstation --logind-lid as the user tty1 logs in, so the user's ~/.config/sndstation/system.json is merged over the shipped one. With no such user, it uses the shipped policy alone.
  3. The launcher prints a logind drop-in and exits before touching the display. sndstation-lid-apply writes it to /etc/systemd/logind.conf.d/sndstation-lid.conf:

ini [Login] HandleLidSwitch=suspend # ignore for keep-playing and off HandleLidSwitchExternalPower=suspend # likewise HandleLidSwitchDocked=ignore # logind's default, whatever the policy

It replaces only a drop-in that carries its own marker line. One that someone else wrote is left alone, and the script says so. 4. logind starts and reads it.

A change applies from the next boot. logind is never restarted under a running session. sndstation-lid-apply --print shows what would be written. Removing the package removes the unit, its link and the drop-in.

In code: lidPolicy() reads the merged setting, lidPolicyFrom(json) does the same on a file already read, lidPolicyName() gives the string, and logindLidDropIn(policy) gives the drop-in text.

Who else reads it

The audio socket's input door (audiodev::readSocket(), see audio-device.md §4) does a one-shot scan: open(dir, psDir, HallkeyConfig{}, false), with no hallkey and no hotplug watch. It takes its answer from the rows. Each row carries has and on (the switches the door carries and which are on, kept current by poll()) and error (the errno when it couldn't be opened), so a consumer never parses note.

Proposal: events, not polling (for discussion)

Not built. Today the app calls poll() once a frame, as above. This is how the SDK could tell every program about switches, cards, the battery and the network without anyone polling, and it is what the system volume in audio-levels.md needs to follow a headphone plug while an app runs (today it follows a card change, and an app can call AudioOut::refreshEndpoint()).

The SDK already has the pieces. They are apart, and two of them poll:

What Today
lid, headphone and line-out sockets, other switches DeviceEvents::poll(), called by the program once a frame. No program calls it yet
battery sysfacts::readBattery(), re-read by each program on a timer of its own (the launcher: every 30 s)
the card played to (a USB interface coming or going) AudioOut::service(), which reads /proc/asound every half second
network the launcher's alone

Every one of these has a kernel source that wakes a reader when, and only when, something changes:

What Woken by
switches the evdev nodes DeviceEvents already holds open, and inotify for nodes coming and going (already there)
a socket whose only detect is an ALSA control ALSA control events (snd_ctl_subscribe_events on /dev/snd/controlC*, alsa-lib, already linked for MIDI). No amixer, no polling
cards coming and going the kernel's uevent netlink socket (sound subsystem)
battery: charging, full, plugged the same uevent socket (power_supply change events)
network rtnetlink: links and addresses

So:

  • One SDK thread sleeps in epoll_wait on all of them. While nothing happens it costs nothing: it does not run, and it has no timer.
  • What it learns arrives as an SDL event, in the event loop every app already has, beside a gamepad being plugged in. That is one event type, registered once (SDL_RegisterEvents), with the kind in user.code: Switch, Battery, Audio, Network. An app that ignores the type is unchanged. It is an event, not a callback, so the app decides when to act: it handles the event where its loop gets to it, on its own thread. A callback would run app code on the SDK's thread, and every app would need locks for it.
  • It does the platform's part first:
  • on a headphone plug, the profile's route and mute (one amixer fork, on a plug only, and never on the audio thread);
  • on a card coming or going, AudioOut's move to it;
  • in both cases, the switch of endpoint and volume.

Then it posts the event. An app that leaves the volume to the SDK needs to do nothing at all. An app that shows the volume, or wants to fade rather than jump, looks at the Audio event. - DeviceEvents::poll() and AudioOut::service() stay, as no-ops once the thread runs, so a program that calls them today keeps working.

The one thing the kernel does not announce everywhere is the battery percentage: some fuel gauges send a change event as it drops, others only on charging and full. On those, "low" can only be found by reading capacity, and the question is how rarely (question 2 below).

Open questions

  1. The thread in each SDK program, or one platform process that sleeps on the same sources for every program? Either costs nothing while nothing happens. The process also covers ports and programs outside the SDK, but it is one more thing beside a real-time app, and it still has to tell the app.
  2. Battery percentage on a gauge that sends no change event: read capacity how rarely, or only report charging, full and plugged?

Other operating systems

Evdev and inotify are Linux's (src/deviceevents_linux.cpp). Any other build gets src/deviceevents_null.cpp, the way MIDI has midi_null.cpp. There, only the hallkey door can answer, and scanned() says no evdev on this OS.

Testing without a unit

tests/test_deviceevents.cpp needs no hardware:

  • Pipes stand in for evdev nodes, through addEvdevFd(fd, has, onNow, name). The test writes struct input_event records into them.
  • setEvdevOps({probe, state}) swaps out the ioctls, so a FIFO in a temp directory passes for a node. That's how hotplug add and remove run in a temp dir standing in for /dev/input, and how SYN_DROPPED gets its re-read.
  • A fake power_supply directory drives the hallkey door, configured and not, through open(..., HallkeyConfig) and addHallkey(path, closedValue).
