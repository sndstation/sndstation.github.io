The lights around the analog sticks

Part of the sndstation design. Built: include/sndstation/leds.h, src/leds.cpp, config/leds.json, system/70-sndstation-leds.rules, sndstation --led-test and --led-slots, and test_leds. Nothing draws on the rings yet: this is the layer that makes them a thing the rest of the program can draw on without knowing which handheld it is running on.

Why it is its own layer

SDL cannot reach these lights. Its LED call speaks only to controllers it has a HID driver for (DualShock, Switch Pro); these are a microcontroller on the board, on a serial port, behind a power switch, and every family does it differently. Worse, the same board does it differently under different kernels: an RG40XX H's chip is ttyS5 with a battery-driver power file on Anbernic's kernel, and ttyS2 with an LED-device power switch on ROCKNIX's mainline one.

So the program sees two rings of logical LEDs, LEFT and RIGHT, each with a count, and everything else is a fact about the unit, in leds.json:

leds::fill(leds::Ring::Left, {0xFF, 0x6A, 0x00});
leds::set(leds::Ring::Right, 3, {0, 0xD4, 0xC8});
leds::commit();          // one write for both rings, from a worker thread

count(), addressable() and describe() are all a caller ever needs to ask. A device that only has a few preset colors reports one LED per ring and shows the nearest preset to whatever is drawn, so drawing code written for the full-color rings degrades instead of branching.

Isolated by unit

leds.json is keyed the way audio.json is: the unit's id (the SOC ID on the ABOUT page), the board model (/proc/device-tree/model), then "*". Unlike audio.json the matches are merged, widest first. Wiring is a fact about a model, shared by every unit of it, so the shipped entries are per model; what one unit needs differently is all its own entry says, in ~/.config/sndstation/leds.json:

"H700-…": { "rings": { "right": [4, 5, 6, 7, 0, 1, 2, 3] } }
"H700-…": { "enabled": false }

The rings map is logical index → wire slot, and the convention it maps onto is index 0 = North, clockwise, seen from the front (0 N, 1 NE, 2 E … 7 NW), so drawing code can point at a direction.

A map is measured, never extrapolated. The first maps shipped for the RG40XX H and RG CubeXX were built from two or three positions per ring, on the assumption that the rest carry on evenly round it; on the box they were wrong — the right ring skipped a position — so the slots do not simply run round in order, and both entries went back to the wire order, marked unmeasured. Compass names and "clockwise" were also read two ways in the reports that went into them.

So --led-slots asks about every slot, one at a time and at the holder's pace, as a clock position seen from the front:

$ sndstation --led-slots
  slot  0> R 9
  slot  1> R 7:30
  …
"rings": { "right": [6, 5, 4, 3, 2, 1, 0, 7],
           "left":  [8, 15, 14, 13, 12, 11, 10, 9] }

It computes the map from the answers and prints the entry to paste; a position given to two slots, or to none, is reported and the map refused rather than filled in. --led-test then lights the rings in logical order and prints the compass point each step should be: a correct map walks both rings N, NE, E… clockwise.

Whether two units of one model can differ — a ring board that fits more than one way round — is not known. That is what a unit entry is for: the model's map is the first unit measured, and a unit that differs overrides rings alone under its own unit id.

Nothing is guessed at

  • Nothing is touched until the first commit(). A unit with lights and a program that has not drawn on them leaves them as the system left them.
  • The serial port is found by the UART it is wired to (node:5001400.serial, matched against /sys/class/tty/*/device), never by a ttyS number alone, which comes from device-tree aliases. A port that matches neither the node nor an explicit path in the entry is not opened: on another board the same number can be the Bluetooth chip.
  • The power switch is whichever listed form is present — led:<name>, file:<path>, gpio:<chip>:<line> (the character device, not the sysfs numbers mainline now allocates from 512) or none.
  • A commit that changes nothing sends nothing, so drawing code can commit every frame; changes are capped at 30 a second and a burst coalesces into its last state.
  • Around a system sleep the rings go dark and the chip unpowered before the sleep command runs, and the last frame is sent again after: the chip forgets everything when the board sleeps.

The two protocols

ch32-frame — Anbernic H700 (RG40XX H/V, RG CubeXX)

A CH32V003 on the H616/H700's UART5, 115200 8N1 raw:

[mode, brightness, 16 × (R, G, B), checksum]      checksum = sum & 0xFF

Verified on an RG40XX H under a ROCKNIX kernel: slots 0-7 are the right ring and 8-15 the left, each taking its own color (one LED lit at a time, by eye). Mode 1 is plain color and is all this sends; the chip's own effects (2-4 breathing, 5-6 rainbows) are animations the program can draw itself, in time with the music, which the chip's cannot be. Dark is mode 1 at brightness 0.

power port
mainline (ROCKNIX) /sys/class/leds/rgb:kbd_backlight/brightness ttyS2
vendor (Anbernic, Knulli) /sys/class/power_supply/axp2202-battery/mcu_pwr ttyS5

Sources: ROCKNIX's quirks/platforms/H700/bin/analog_sticks_ledcontrol and its uart5 device-tree patch; Knulli's allwinner/h700/.../knulli-rgb-led.

aislpc-preset — XiFan XF40H and kin (RK3326, RK3562)

One byte per command at 9600 baud, each sent several times: 1=G 2=B 3=R 4=G+B 5=R+G 6=B+R 7=white (rainbow on some boards) 8=flow 9=off, 17-24 breathing; some boards ignore everything until an init byte 0x20 + leds/4 − 1. No arbitrary color, no per-LED control. Every number that differs between boards is in the entry (presets, off, init, repeat, gap_ms), and a color drawn is shown as the nearest preset by hue, so a dim orange is still orange.

Not verified here, so the shipped XF40H entry is disabled: the protocol is bmdhacks' reverse-engineering on the RG52 Mini (dArkOS) as ported in AveyondFly's ROCKNIX fork, and the XF40H's port (ff178000.serial), power line (GPIO2_A1, assumed gpiochip2:1), init byte and repeat count are all unconfirmed. gpioinfo and /sys/class/tty/*/device on the unit settle them.

Permissions

sndstation does not run as root, and should not — it hosts third-party plugins. The serial port is the dialout group's on Debian already; the power switch is a sysfs attribute no group can write, so on a handheld the package's install script links in a udev rule handing exactly that file to dialout, for both the mainline and the vendor form. A rule only applies when its device appears, which is at boot, so the package's install script replays the "add" for those two devices alone; without that, installing on a running box changed nothing until a reboot. The user sndstation runs as has to be in dialout. The XF40H's GPIO chip is not handed over yet: a GPIO bank holds more than one LED's power, and that rule waits until the line is confirmed.

Checking a unit

sndstation --led-slots    # MEASURE: every wire slot, asked about one at a
                            # time; prints the "rings" entry
sndstation --led-test     # CHECK: each logical LED in turn, with the
                            # compass point it should be, then both rings in
                            # their stick colours, then dark

The first line says what was found — driver, port, power switch, rings, and which entries it came from — or exactly why nothing was.
