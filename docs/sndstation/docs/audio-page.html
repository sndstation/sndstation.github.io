Audio: one model, one decision-maker, a page that shows it

How the unit's audio is set, kept and decided, and why the AUDIO page is built the way it is: launcher/audiosetup.cpp and the files beside it, on the SDK's audiounit, audiodev and mixerio. The overview, who opens the device and when, is audio-stack.md. The device layer underneath (the card, the buffer, the test signals, MDFourier) is audio-device.md; the volume and the maximum are audio-levels.md.

The rule

Audio is set and tested in the launcher. Every app opens its sound through the SDK (AudioOut) and follows the same decisions without working anything out itself: which card plays, which output on it, the route, the maximum, the volume. Programs outside the SDK get what the launcher's startup apply puts on the card, and nothing more.

Why it is built this way

The page before this one worked the same facts out in several places from several copies — the route in the page (from its unsaved profile), in AudioOut (from the file), at startup (from a third lookup) and in the wizard; which output played in three functions; which card in four — and more than one of them wrote to the card. Nearly every regression was two of them disagreeing. It also ran amixer for every read and write, about 230 ms a call on an RG351V, and most of its modes (not watching the socket during a test, a frozen title, delayed writes) existed to hide that.

So now:

  • One set of functions decides (audiounit.h): from the cards present, the socket, the unit's set-up and its choices, which endpoint plays and what playing it writes. They read nothing, so they are tested as a table (tests/test_audiounit.cpp), and AudioOut, the startup apply, the volume keys and the page all call them.
  • One writer: AudioOut applies routes and maximums when it opens, when the card changes, and when asked (refreshEndpoint). A headphone plug only swaps the route (where the set-up says software must: the rk817's mux, the H700's amp) and the volume to that output's: no maximum written, no card looked for, nothing reopened. Every program that plays follows the plug, not only the AUDIO page. The page saves a change and asks its own AudioOut to apply it, and shows what that output reports. While the set-up by ear runs, the output is told to keep its hands off the route (holdRoute).
  • The mixer in-process (src/mixerio.cpp): amixer's four verbs through alsa-lib, printing exactly what amixer prints so the parser proven on seventeen units stays the reader. Under a millisecond a read.

Why each unit has a profile of its own

Nothing about a handheld's audio can be read off its device tree.

Of seventeen RK3326 units surveyed, seven report the same board model and the same compatible — and they do not behave the same: five route audio cleanly, two play out of both outputs at once. An image builder patched a dts somewhere and the string stayed put. Whether the headphone detect bit means what it says, and which mux item reaches which physical output, are facts you establish by plugging something in and listening.

So nothing is guessed: one unit's answer given to another would take a working box and silence it. A board the team has calibrated itself, on our own image, has a preset (below); every other unit has only what was heard on it. The user's audio.json is keyed by the unit — the SOC ID row on the ABOUT page — else the board model, else the built-in card, and only that key is read (below).

The wizard is offered once, never forced. A box whose audio already works — every desktop, and any handheld whose dts happens to be right — has nothing to calibrate. So on its first run the launcher puts up a card only on a handheld (a device tree, and a card with a speaker/headphone route) that is not set up, after the gamepad's own first run: A starts the wizard, B skips it, and the skip is remembered for the unit (~/.config/sndstation/setup.json, audio_skipped). A desktop is never asked, nor a unit its board's preset applies to: it is set up.

Outputs

An endpoint is a place sound comes out:

Endpoint What it is
speaker, headphones the built-in card's two outputs
speaker+headphones both at once, where the board can make it
out a unit that cannot tell which of the two plays (no usable detect bit): Automatic plays the speaker's route, the socket does the rest
builtin the built-in card of a unit nobody has set up: nothing is routed
usb:<vid:pid> a USB interface
card:<id> any other card: HDMI
default the system's own device: no card of ours

Plays on is one choice among them, each a complete answer to where sound comes out:

  • Automatic: a USB interface when one is plugged in; else the headphones when they are in and the unit can tell; else the speaker. HDMI is never chosen automatically.
  • There is no "off": "neither speaker nor headphones" is choosing another card, and something always plays. A chosen card that goes away falls back to Automatic until it is back.
  • Only what this unit can make is offered. The set-up by ear finds it out:

rk817 with a speaker switch yes as heard
rk817 with a plain mux where one item plays both as heard
a socket that cuts the speaker itself no no: only Automatic is offered
  • A unit nobody has set up offers Automatic, Built in and any other card, and leaves the built-in card's routing as the system set it.
  • Built-in and another card at once is not offered: two clocks need a second stream and drift correction.

Set up by ear

AUDIO / Set up by ear derives the whole profile by asking, at each step, the one question a person holding the box can answer: where do you hear it — speaker, headphones, both, or nothing. Short beeps play throughout: 440 Hz, 120 ms in every 600, at −18 dBFS (TestTone::Beeps, BEEP_LEVEL), never a held tone. The page's volume is not applied to them, so a turned-down volume cannot make "nothing" a wrong answer; their level and their gaps are what keep a small speaker safe meanwhile.

What it concludes goes in the unit's set_up (detect, route_control, speaker_switch, and a route for each output it can make: speaker, headphones, speaker + headphones where it heard both, and out, what Automatic plays where it cannot tell). While it runs, the page's sound output keeps its hands off the route. What it observed is kept beside it, in survey: the raw detect-bit readings plugged and unplugged, what was heard in each state, whether the jack switches mechanically, whether the speaker bleeds, whether the channels are swapped — plus the card's whole control list and the subset of it that could move sound around and that the profile never touches.

That last one is written even when it is empty: "all of them accounted for" is a finding once it comes from twenty boards. The point of keeping the observations is that the conclusions can be re-derived later, from a different theory, without going back to the hardware.

Two things the surveys settled that are not obvious:

  • detect: "mechanical" — some sockets have no detect bit at all and switch the speaker themselves. That is a fourth state, not a broken version of one of the other three.
  • speaker_switch — on rk817_ext the speaker mute is factored out into a second control (Internal Speakers), so setting the mux alone leaves both outputs playing. Empty where the mux suffices. It is also what makes "speaker + headphones" a choice there: the headphones' route with the speaker left on.

The pages

  • Device: where sound comes out (it was Plays on). ◂▸ steps through the choices; A lists every card (CARDS).
  • Sample rate and Buffer size: the playing card's, live, offering only what the device answered when asked; kept per card.
  • An output (A on its row): its user level, Play on it; for the built-in card, Set up by ear and, once set up, Corrections (plug detection, swap, the speaker switch).
  • User level: a gain on the samples, in software, before the chip; every app plays through it (audio-levels.md).
  • System levels: the chip's own controls. Its playback levels are the playing output's ceiling, and nothing else sets it: see below.
  • TOOLS: USB interface (while one is plugged in), Diagnostics, MDFourier, each a view of its own.

The test sound is pings peaking at full scale, played at the volume: what a loud app does at this volume. The steady sine stays at -12 dBFS (a continuous sine is the signal that cooks a small speaker), and so does the set-up by ear, which runs before any maximum exists.

The page plays into the launcher's stream (launcher/audio.h), opened when the launcher starts: its test sounds are a source on that stream's mixer from the page's open to its close, at the user level, or past it in System levels, where an output's ceiling is judged (on headphones, at the user level there too). It is also the one place that reopens that stream: a card, a rate, a buffer size (audio-stack.md). Built alone (--shots, the tests), it has a stream of its own, opened and closed with the page.

What holds across the views

The views are also listed in launcher.md. What holds across them:

  • The title line answers the question people open an audio page with: where is the sound going, and is anything plugged in. It shows what the page's own sound output reports, so it is never stale.
  • The bottom bar says what the selected row does (its tooltip), and for a choice, what that choice does. A message takes its place while it lasts. There is no help box: the list has the room.
  • Nothing waits to be saved. Every change is written as it is made, and "✓ Saved" shows in the title bar for a moment. --shots writes the caption as 09a-audio-saved.
  • Rows that cannot mean anything are not offered: a unit not set up has no Corrections.
  • Choices take ◂▸ and show arrows when selected; rows that open a view take A and say so.

Every reading is in DIAGNOSTICS, with a one-sentence verdict at the top and the figures underneath. Every control is in SYSTEM LEVELS.

Plays on and Cards: which card plays

  • Device chooses where sound comes out: Automatic, an output of the built-in card, or any other card that plays, by its id (Outputs). The sound moves there at once (AudioOut::setDevice, then refreshEndpoint). Each card keeps its own rate and buffer size.
  • Cards (A on Device) lists every card, built in and USB, playback and capture alike, by name, with its direction and, where the card says them, the format and rate of each direction. A plays to the card under the cursor, and so does Automatic at the top.
  • The list follows plugging. The page reads /proc/asound twice a second, so a card plugged in or pulled out appears or goes while the page is open, and the page's sound output follows it (audio-device.md §3.3, Hotplug).
  • An HDMI card plays through ALSA's hdmi device where ALSA's own file for its driver defines one (/usr/share/alsa/cards/<driver>.conf): hdmi:CARD=vc4hdmi,DEV=0 on a Raspberry Pi. The Pi's HDMI hardware (vc4-hdmi) takes IEC958 frames and nothing else, so hw and plughw refuse every format SDL has and nothing sounds; ALSA's device encodes them. Automatic never picks a display output: on a Pi it takes the headphone socket, and Plays on picks vc4hdmi for a screen with speakers.

--fake-audio m8 answers as an RG35XX SP with a Dirtywave M8 plugged in (Codec plus an S24_3LE-only, 44.1 kHz M8). --shots writes the list as 11b-audio-cards.

USB I/O: is it there, and does each output and input work

While a USB card is plugged in, MORE has a USB interface row: its id, and how many channels it plays and records (M8 · 2 ch out · 24 ch in). The row appears and goes with the card, and the page says so in its help box wherever it is ("USB interface M8 plugged in: 2 ch out, 24 ch in."). A on the row opens USB I/O:

 MAIN T1  T2  T3  T4  T5  T6  T7  T8  MOD DLY REV
  • What it is: name, and the format, channel counts and rates of each direction, from the card's own stream file (audio-device.md §3.3), as AudioOut's choice reads them.
  • Play through it: A makes the card what Plays on chooses. Left goes back to the built-in card, since Automatic would land on the USB card again.
  • Test output: Off, Out 1 (left), Out 2 (right), Outs 1 + 2. The tone is the page's test tone (testtone.h): a steady 440 Hz at -12 dBFS, held by a lease, so leaving the view, the page or the launcher silences it. Testing moves the sound to the card first, because the tone plays where the sound goes. AudioOut plays stereo, so a card's first two outputs are the ones offered.
  • Inputs: a meter on every capture channel, 0 to -60 dBFS, falling at 20 dB a second, teal, then amber from -6 dBFS, and orange at full scale. A mark over a meter counts samples at full scale; X clears them. Channels that come in pairs are grouped, named under the pair. An M8 recording 24 channels is named in Dirtywave's order (MAIN, T1–T8, MOD, DLY, REV); other cards by number.

The meters are InputMeter (audioin.h). It opens the card's capture on alsa-lib, not SDL, because SDL2 opens only 1, 2, 4, 6 or 8 channels. It opens every channel at once, in the card's own format (S24_3LE, S32_LE, S24_LE or S16_LE), on hw, so a level read is the level the card sent. It is open only while USB I/O is on screen. Pulled out, the view says nothing is plugged in and the inputs close; plugged in again, they reopen. --fake-audio m8multi and the tests make up levels instead of opening a device. --shots writes the view as 11c-audio-usb.

Editing the mixer

Every control the card publishes is editable in place, live, and nothing about which controls exist is hardcoded: a level steps in the card's own discrete units, a switch toggles, an enum cycles its own published items. Anything moved joins the unit's built_in.mixer list at its new value (a level with its range) and is put back at startup from then on (a dot marks those), saved as soon as it settles; X drops a control back out of the list. A playback level is the playing output's ceiling instead: moved, every playback level is kept at once as that output's maximum, and put back whenever it plays (audio-levels.md). The view shows PLAYBACK and ROUTING; the switches, and capture and the rest, are each behind a row of their own that A opens. A level is drawn as a bar and its dB (or percent); the bottom bar gives its number and range, for the reason below.

There is no per-card table of "the controls that matter", and there cannot be one. Seventeen rk817 units with the same codec and the same board string behaved three different ways; any curated list would be wrong on some unit within a week, and nothing about a board predicts which. What ALSA does say on every card is what KIND each control is — pvolume, pswitch, penum — and that is all an editor needs. Which ones matter is a per-unit fact, established the way every other per-unit fact here is: a person listens, and the file remembers. That is what makes an H700, a USB DAC or the next clone work with no new code.

The list stays in the card's own order rather than being sorted by likely relevance: its other job is to be what you cross-check against amixer scontents, and a page that agrees with the tool is worth more than one that puts the interesting row first.

Levels are discrete, and shown that way

201 (79%) 0:255, not 79%. The value and its range are the granularity — a 0:255 control has 256 positions and a 0:15 one has 16 — and which you are on decides whether the next press is a nudge or a jump.

The fine step is 1: the device's own granularity, not a fraction of a range invented here. Y/A take a coarse step (a sixteenth of the range, at least 2) as a concession to a d-pad rather than to the device. Y is west and A is east, so the face pair points the same way left/right does. The bottom bar names both for the control under the cursor ("◂▸ moves it 1, Y/A 15 (now 201 of 0:255)."), because how fine the control is and how fine you are being with it are two different questions.

A percentage step was worse than imprecise: 5% of a 0 - 15 control is 0.75 units, so it landed back on the integer it started from about half the time and the press did nothing — invisible to anyone watching a percentage, obvious to anyone watching the number. Percent survives in parentheses, and as the fallback for a card that publishes no Limits: line, where there is no unit to step in.

Two ALSA details that bite on real cards

  • A control with both pvolume and cvolume carries two independent values, and amixer sset 'Master' 84% sets both — so adjusting output would drag the capture gain along with it (on rk817_ext, playback 79% and capture 100% collapsing onto one number). Writes to those name playback. amixer itself applies a value before it reads a direction word after it, so sset 'Master' 84% playback still set both; the in-process sset (audio-device.md §1) honors it. An undirected volume is one value serving both, and is written undirected.
  • amixer cost about 230 ms per call on an RG351V: a fork, an exec, and an ALSA config parse off slow storage. See audio-device.md §1.

The maximum, and the signal that sets it

An output's maximum is the set of hardware levels it plays at: its 0 dB. The volume only turns down from it, so nothing an app does goes louder.

It is defined as what a full-scale sample produces, so it is set with one. Judged with pings at -12 dBFS (as the first ceilings were), an app reaching full scale plays 12 dB louder than anything heard while setting it: four times the amplitude, sixteen times the power, enough to clip the amplifier or rattle the speaker. The SDK clips anything past full scale, so full scale is the most the analog stages ever see.

System levels is where it is set, by ear: turn on the test sound (pings at 0 dBFS), open System levels, and the pings play past the user level, so what is heard is the ceiling itself. Raise the playback levels until it distorts, rattles, or is too loud, and back off; each move is kept as it is made. On headphones the pings stay at the user level. MDFourier finds it by measurement instead: record it on the line output at each setting, the highest that does not clip. It measures these levels, as it plays past the user level.

System defaults: a calibrated board's preset

config/audiopresets.json, shipped, holds one entry for each board the team has calibrated on our own image: what the set-up by ear concluded there, the speaker's maximum from SYSTEM LEVELS, the card's rate and buffer size, and the card as it was. A unit an entry applies to starts set up, at those levels. It is not offered the set-up by ear, and the first start's bring-up never runs on it.

The match is all or nothing (audiounit::presetApplies):

  • the board's model (/proc/device-tree/model);
  • the built-in card's ALSA name: A100 Audio Codec, not its id, which the A100 and H616 codecs share;
  • every control of the card: the same ones, each with the same capabilities, range and items. A control the card has and the entry does not is a miss;
  • the control the socket is read from, where the set-up follows the plug.

Any miss, and the unit is as it would be with no file: the log says what differed (audio/preset: … does not apply: …). A kernel that renames a control or changes its range sends the unit back to the set-up by ear, not to a wrong route.

The unit's own wins, and nothing is copied. audiounit::load fills in from the preset what the unit does not keep for itself: its set-up, the built-in card's rate and buffer size, an output's maximum. save writes none of it back: a part that equals the preset's is not the unit's own. So an entry corrected in a later release reaches every unit that has not changed that part. A set-up made by ear on the unit is its own, whatever it concluded.

At every start (applyStartupMixer), before what the unit keeps by hand and the playing output's route and maximum, every level and switch the entry holds is put back, only where it differs. A control moved behind the page, with amixer or by another program, does not stay moved.

An entry has no maximum for headphones: a speaker is the board's, headphones are not, and the first plug's volume of -18 dB (audio-levels.md) is what covers them.

Making an entry. Calibrate the unit: Set up by ear, then SYSTEM LEVELS. sndstation --audio-preset prints its entry, from its audio.json and the card as read. A person reads it over, fills in who calibrated it and on which image, and adds it to the file. The file's own comment has the format.

The match cannot see a driver that changes what a control does without renaming it: the entry still applies, and is wrong. When a card's driver changes, its boards are calibrated again.

Not built yet: the page saying whether the unit is on its board's defaults, and going back to them (#268). Until then, removing the unit's entry from audio.json does it.

Kept: audio.json, version 3

The user's ~/.config/sndstation/audio.json, one entry per machine, under its key: the chip's ID (the SOC ID on ABOUT), else the board model, else card: and the built-in card's id. Only that key is read.

{
  "version": 3,
  "RK3326-URKC08010-A599D7394C5B58B6": {
    "set_up": {
      "when": "2026-11-05 13:22",
      "detect": "inverted",                     // normal | inverted | none | mechanical
      "route_control": "Playback Mux",
      "speaker_switch": "Internal Speakers",    // a second control, where there is one
      "speaker_alone_with_headphones": false,
      "routes": {
        "speaker":            { "item": "HP",  "speaker_switch": "on",  "heard": true },
        "headphones":         { "item": "SPK", "speaker_switch": "off", "heard": true },
        "speaker+headphones": { "item": "HP",  "speaker_switch": "on",  "heard": true },
        "out":                { "item": "HP",  "speaker_switch": "on",  "heard": true }
      },
      "survey": { ... }                         // what was observed, kept beside it
    },
    "plays_on": "auto",
    "built_in": {                               // one stream: shared by its outputs
      "rate": 0, "buffer": 256,
      "mixer": [ { "control": "Mic Capture Gain", "value": 3, "range": [0, 15] } ],
      "brought_up": true
    },
    "endpoints": {
      "speaker": { "volume_db": -6,
                   "maximum": [ { "control": "Master", "value": 180, "range": [0, 255] } ] },
      "headphones": { "volume_db": -21 },
      "usb:16c0:048a": { "volume_db": 0, "rate": 44100, "buffer": 256, "raised": true }
    }
  }
}
  • Hardware values are native units: a level's raw number with the range it was read in, a switch's on/off, an enum's item. A level kept in a range the driver no longer reports (a kernel that turned 0:255 into 0:63) is not applied, and says so. The driver's dB is only ever shown, never kept.
  • volume_db is the software gain, below the maximum: ours, exact.
  • Only the set-up by ear writes set_up (and Corrections, by hand). A unit without one is not set up, whatever else it keeps: a mixer edit or a maximum never makes it look set up. Its board's preset, where one applies, sets it up without writing here (above).
  • Speaker, headphones and both share one rate and buffer (built_in): one stream, and separate values would reopen it on every plug. A USB or HDMI card keeps its own.
  • A file of any other version is deleted when found, with the device, sample_rate and buffer_frames the old page wrote into the user's system.json, and the unit starts again. Nothing is converted.
  • Every save is a patch of the file as it is (audiounit::patch), so two holders of the unit cannot undo each other.

system.json keeps what is the platform's: the output format, dither, realtime priority, core, alsa_pcm, and the default rate and buffer size a unit has not changed.

What ALSA does and does not promise

  • The raw integer is the firm part: writing 180 gets the same result every time on the same driver. It need not be the register value.
  • dB is metadata the driver author wrote (TLV): missing on many controls, wrong on some.
  • amixer's percent is a third mapping, linear in the raw range.
  • A range can change with the kernel: hence the range kept beside each level.
  • amixer applies a value before it reads a direction word after it, so amixer sset 'PCM' 50 playback set the capture level too. mixerio honors the direction (Two ALSA details, above).

Not yet tried on a unit

Still to try on hardware: the in-process mixer on each family, "speaker + headphones" on an rk817_ext and an H700, SYSTEM LEVELS' full-scale pings on a speaker, the startup apply on a unit with a chip ID, and a board's preset on a unit (test_audiopreset checks it on the H616 fake).
