The audio stack

How sound gets from a program to the speaker on a sndstation unit: who opens the device, who keeps it, and how it passes from the launcher to an app and back. This is the overview. The details are in audio-device.md (choosing the card, formats, timing), audio-levels.md (volume and maximums) and audio-page.md (the AUDIO page).

Parts of this are planned and not built yet, first written up as sndstation#251. Each section says which parts: Now is what the code does today, and #251 is what it is moving to. The order they are built in is the table at the end.

The rules

  1. One owner per process. Exactly one place in a process opens the audio device and the MIDI ports, and keeps them. In the launcher, that is the launcher. In an app, it is the app. Everything else plays into the owner's stream and never opens, closes or reopens a device.
  2. ALSA directly, on a unit. Playback goes from AudioOut to alsa-lib, through the SDK's own stream (alsastream). SDL may start its audio subsystem and list devices, but on Linux it never plays. SDL's own stream is for macOS and Windows development builds, and for tests that use its disk driver.
  3. Open once, close rarely. Opening and closing a device is what pops. The owner opens at start and closes only when it must (see "When the device is closed" below). Every open, close and reopen fades.
  4. Leave nothing behind. A process that started with the device free hands it on free, and hands on its environment as it found it (AUDIODEV, SDL_AUDIODRIVER).

The layers

  your sound                 a synth, a sampler, a plugin, a test tone
      │  render(out, frames) on the audio thread
      ▼
  audiomix::Mixer            sums the sources, fades each one in and out
      │  the owner's RenderFn
      ▼
  AudioOut                   which card, the conversion to its format, dither,
      │                      the system volume, meters, health, card changes
      ▼
  alsastream                 the SDK's alsa-lib stream: snd_pcm_writei on the card
      │
      ▼
  ALSA  →  the card  →  speaker / headphones / USB interface
  • A source knows nothing about devices. It fills interleaved float stereo when asked, at the rate it is told (rateChanged()).
  • AudioOut is the device.
  • It picks the card the way handhelds need: the card itself (hw:CARD=<id>,DEV=0), not default, skipping display outputs and virtual cards (audio-device.md §3.3).
  • It converts to the card's format in one loop that also counts clips and dithers.
  • It applies the system volume, ramped.
  • It keeps the callback's health: gaps, underruns and CPU.
  • It follows a USB card that is plugged in or pulled.
  • alsastream is what plays. An AudioOut is handed the unit's settings (rate, period and format, from the AUDIO page) and its realtime priority (rt.h). SDL is not on that path.

Now:

  • The launcher has one stream and a mixer (launcher/audio.h). An app's AudioOut has its own render function, which is the app's mix.
  • On Linux, AudioOut plays every device through alsastream: the card it chose, AUDIODEV or audio.alsa_pcm as given, and default with whatever the system put behind it (a plug, a dmix, a sound server's ALSA plugin). SDL's audio is started on its ALSA driver for the log's device list, whatever it would pick first (audio-device.md §3.0).
  • Not yet measured on a unit with a sound server (KNULLI) or a dmix: alsastream starts with the whole buffer queued and blocks in snd_pcm_writei, as aplay does. Underruns (AUDIO → Diagnostics) and latency through default against SNDSTATION_AUDIO_STREAM=sdl on the same unit settle it; if a server needs it, default alone gets a smaller start threshold.

Opening

The owner does this once, when it starts:

#include <sndstation/audioout.h>
#include <sndstation/rt.h>

AudioOut::Settings set = AudioOut::loadSettings();   // the unit's: card, rate, period, format
rt::applySettings(set.realtimePriority, set.cpu);     // the audio thread's priority and core
AudioOut out;
out.open(set, &render, &rateChanged, this);           // opened paused
out.start();                                          // fades in

loadSettings() reads the platform's system.json and the unit's audio.json. The AUDIO page writes the latter, and every program on the unit opens with the same settings, so an app plays on the card, at the rate and period the user set up.

With no device (a headless run with --shots, or nothing that opens), open() still succeeds, and the owner calls out.pumpManual(dt) from its own loop. Everything above the device keeps running and stays testable.

While it runs

Once a frame, on the main thread, the owner calls:

Call What it does
out.service() a USB card plugged in or pulled: the stream moves to the card the rules choose now, and the sources are told the new rate
out.followJack() the headphone socket: the right output's volume and maximum
out.pumpManual(dt) only with no device: renders the time that passed

Only the owner changes the device. In the launcher, the AUDIO page is the only place that reopens it: a new period (reopen()), rate (setRate()) or card (setDevice()). Each of those fades out, reopens and fades in (audio-device.md §3.6).

The system volume is not the owner's. Vol± and the AUDIO page set it per output, every program shares it, and AudioOut applies it after the render function (audio-levels.md).

Playing into the stream

A page, the game or a plugin is a source attached to the owner's mixer (audiomix.h):

struct Tone : audiomix::Source {
    void render(float* out, int frames) override { /* add into out */ }
    void rateChanged(int rate) override { /* re-tune */ }
};

Tone tone;
launcherAudio.mixer().attach(&tone);   // fades in from the next block
// ...
launcherAudio.mixer().detach(&tone);   // fades out; returns once the audio thread let go

The mixer applies the system volume to each source, unless the source says it applies its own (ownVolume()): the AUDIO page plays past it while an output's maximum is judged. A source fades in when attached and out when detached, and detach() returns once the audio thread has let go, so the source may then be destroyed.

Now: the AUDIO page and the game are sources on the launcher's stream. Built alone (--shots, the tests), each has a stream of its own, opened and closed with it, as before.

A CLAP plugin is played the same way. ClapPlayer opens no device and no MIDI ports:

  • In the launcher, it is a source on the launcher's mixer, activated at the stream's rate (rateChanged() activates it again at a new one), and the launcher's MIDI is pointed at it.
  • In an app with an engine of its own, the app activates it (activate(rate, maxFrames)), its audio thread calls ClapPlayer::process() with its notes and parameter changes, timed within the block, and mixes the result itself. The app lists and sets its parameters (params(), setParam()) and keeps its state as bytes in its own files (saveState(), loadState()). A restart the plugin asks for is answered at its next block: silence while it is activated again on the main thread (update()).

MIDI

MIDI follows the same rule. The owner starts it (midi::start()), listens to the unit's inputs (midi::listen()), and stops it (midi::stop()) at the same moments it closes the audio device. A page or a plugin never starts or stops MIDI itself.

In the launcher that is LauncherMidi (launcher/launchermidi.h): started with the launcher, it hands what arrives to the page in front that takes it (a played plugin) or to nobody, and a page's sink is taken away only once a message on its way to it has been delivered. Closed for the hand-over and every way out, let go of while the screensaver is up and while the unit sleeps. The MIDI monitor opens every port itself, each with its own sink, so while it shows the listening is paused and the ports are its; the launcher listens again after.

The launcher's life, and the hand-over

The launcher is one turn of a loop. sndstation-session starts it, the launcher replaces itself with the app you pick (exec), and when the app exits the session starts the launcher again. There is never a launcher and an app at once, so the device always has exactly one owner.

When the device is closed

The launcher closes the device only:

  • when it hands over to an app;
  • when it shuts down, restarts or exits, whatever the path;
  • when the screensaver starts, or the unit goes to sleep;
  • when the AUDIO page reopens it for a new period, rate or card.

Nothing else closes it, and it is opened again at the end of each of these but the first two.

Handing over to an app

  1. Fade out, then close, as every close does. The app opens a free card. Two processes can't share a card without a sound server, so the hand-over is a short fade rather than nothing.
  2. MIDI stopped. The app opens the ports it wants.
  3. AUDIODEV as the launcher found it. An AudioOut writes AUDIODEV while it plays and puts it back on its last close, and launch() sets it once more to what the launcher was started with. The app chooses its card by the same rules as when it is started from a shell. (Before this was fixed, an app could inherit the launcher's choice, take it for a user's, and play through SDL's stream instead: see the changelog.)
  4. SDL shut down, then exec. The app gets the display, the pads and the card, in the same process, with SNDSTATION_SESSION=1 in its environment.

Coming back

The app exits, its AudioOut closes (the destructor does it too), and the process ends. The session starts the launcher afresh, and the launcher opens the device as at any start. Nothing is carried over, so a card that was plugged in while the app ran is the one the launcher opens.

Writing an app

  • Open one AudioOut at start, with AudioOut::loadSettings(), and close it at exit. Don't open a second one, and don't close and reopen it to change what plays: mix inside your own render function.
  • Call service() and followJack() once a frame. Leave the volume to the system unless you set appVolume and apply volumeGain() yourself.
  • Don't set AUDIODEV, and don't open devices through SDL. A user who sets AUDIODEV is making a choice, and the SDK honors it.
  • With SNDSTATION_SESSION=1, quitting is going back. Close what you opened, and exit. The session brings the launcher back.
  • Hosting plugins: load them with ClapPlayer, activate them at your stream's rate, and call process() from your own audio thread, or attach them to an audiomix::Mixer. Point your MIDI at them (they are midi::Sinks); never let them open a device.

Rules for SDK contributors

  • Only the owner calls open(), close(), reopen(), setRate() or setDevice(). A new piece that makes sound is a source.
  • No SDL_OpenAudioDevice on Linux. SDL's audio subsystem may list devices and pick its driver; playback goes through alsastream.
  • No setenv("AUDIODEV") outside AudioOut's own writer, which puts it back.
  • Every change to a running stream fades. test_audioout checks for steps.

Diagnostics

The log, in order, says what happened:

  • audio: driver 'alsa', N playback device(s): SDL's list, for diagnosis only.
  • audio: ALSA device '<pcm>' (<why>): which device, and which rule chose it. (AUDIODEV, set outside) in an app started from the launcher means something leaked: report it.
  • audio: <rate> Hz, <frames> frames, handed <format>: what the device accepted.

The stream's health (gaps, underruns, clips, CPU) is on AUDIO → Diagnostics. To check that nothing holds the card during the screensaver, run fuser -v /dev/snd/*.

SNDSTATION_AUDIO_STREAM=sdl plays through SDL's stream on the same device, to compare the two: a developer's switch, and each open through it says so in the log, as does a build that plays through SDL's stream for any other reason (audio: SDL's stream, not alsa-lib's: ...).
