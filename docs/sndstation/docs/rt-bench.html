--rt-bench: measuring the audio thread's headroom

Scheduling changes — a realtime audio thread, nicer helper threads, a reserved core — are easy to make and hard to judge by ear. --rt-bench turns "it seems better" into one number that can be compared across configurations, units and kernels: headroom, the share of each audio period the callback can spend before the card underruns.

Running it

The bench is the SDK's (<sndstation/rtbench.h>), and an app runs it: it hands rtbench::start() its open AudioOut and an rtbench::Instrument (a chord to hold, and a name for it), takes the --rt-* flags with rt::parseArg(), and calls rtbench::frame() every frame. examples/hello does, with its test tone as the instrument (hello --rt-bench); it is the wiring to copy. With app standing for an app that does:

app --rt-bench --rt-noise 4                      # as shipped: SCHED_FIFO 70
app --rt-bench --rt-noise 4 --rt-fifo 0          # baseline: an ordinary thread
app --rt-bench --rt-noise 4 --rt-cpu 2           # audio thread pinned to core 2
app --rt-bench --rt-noise 4 --rt-helpers-nice 10 # helpers lowered

The audio thread's scheduling comes from the platform's system.json — audio.realtime_priority (70 as shipped) and audio.cpu (-1, no pin) — and the flags override it for one run. A baseline has to say --rt-fifo 0 explicitly.

It runs the real program — window, UI drawing, the instrument that is loaded — so what it measures is what the app does on that unit, not what the hardware could do in isolation. After a 3 s warm-up it holds a chord (struck again every 2 s) and steps the callback's load up; at each step it prints a line, and at the end one RESULT line, then quits.

Flag Default
--rt-bench run the sweep, print, quit
--rt-loads a,b,… 0,50,70,80,85,90,95 percent of the period, in order
--rt-step S 20 seconds per step
--rt-fifo P audio.realtime_priority audio thread to SCHED_FIFO P; 0 = ordinary
--rt-cpu N audio.cpu audio thread pinned to core N; -1 = any
--rt-helpers-nice N off helper threads (ss-amixer, ss-leds) to nice N
--rt-noise N 0 N competing threads on every core
--rt-proc 0\|1 0 when alsa-lib's count is available /proc status reads, for the buffer margin (below)

The --rt-fifo, --rt-helpers-nice and --rt-noise switches work without --rt-bench as well, so a configuration that measured better can be listened to.

What it found, and what ships

On an RG351V (RK3326, kernel 7.1.2, 48 kHz / 512 frames, built-in synth), with --rt-noise 4:

audio thread headroom worst late, no added load
ordinary, nice 0 0% — 115 underruns at 50% 12.8 ms
ordinary, nice -20 (as root) 0% — 6 underruns at 50% 5.7 ms
SCHED_FIFO 70 90% 1.7 ms

Without the noise, an ordinary thread still came 4-4.8 ms late 36 times a minute, at irregular spacing (the UI, Mesa, kernel workers); at FIFO 70, never more than 1 ms. A high nice is not enough: an ordinary thread at any nice still shares the CPU fairly, and only a realtime policy goes first.

A Powkiddy RGB30 (RK3566, kernel 7.0.2, 48 kHz / 256 frames, built-in synth, booted rt_group_sched=0 — see "Allowing it") agrees: with no added load an ordinary thread came 18 ms late at worst and underran twice in a minute; at FIFO 70, 1.12 ms and clean. With --rt-noise 4, clean through 90%, failing at 95%.

So the audio thread runs SCHED_FIFO 70 by default, raised by the thread itself on its first callback (rt::audioThreadEnter) rather than through SDL's priority hints, which pick their own number and say nothing when refused.

Pinning, and the helpers: measured, and left off

Same unit and noise, FIFO 70 in each:

headroom failed at worst late, no added load
no pin (audio.cpu -1, shipped) 90% 95% 1.56 ms
pinned to core 2 (--rt-cpu 2) 85% 90% 1.68 ms
helpers at nice 10 (--rt-helpers-nice 10) 90% 95% 1.55 ms

Pinning failed a step earlier, on the same once-a-second ~50 ms stalls as below. That fits how the kernel's reserve for ordinary threads works: it is paid per core, and an unpinned realtime thread can move to another core while one is paying it; a pinned one has to wait it out. One step is within run-to-run noise, but nothing points the other way, so the audio thread is not pinned. Lowering the helpers changed nothing, as it should not: once the audio thread is realtime, no ordinary thread gets ahead of it at any nice. Both stay as flags, for measuring.

Why 95% fails, and why that is fine

At 95% the FIFO thread underran once a second, ~50 ms each time, like clockwork (median spacing 1.01 s). That is the kernel keeping 50 ms of every second, on each CPU, for ordinary threads (RT throttling; on newer kernels the "fair server"): the noise threads starved by a thread that would take 95% of a core get their 50 ms at once. It is the same rule that keeps a runaway plugin from freezing the box — it stalls its own audio instead — and it puts the practical ceiling near 90%.

At a short buffer the failure is not a few clicks but a cascade: the RGB30 at 256 frames underran 1639 times in 11 s at 95%. After an underrun the stream restarts nearly empty, and a callback that takes 95% of every period gains only 5% of one back per period — never enough to refill before the next stall. (The console says each underrun at most once a second, with a count of the rest.)

Allowing it

A user may raise a thread to realtime only up to its RLIMIT_RTPRIO (ulimit -r), which is 0 by default. Without an allowance the raise is refused, said once on stderr —

rt: audio thread: SCHED_FIFO 70 refused (Operation not permitted; ulimit -r is 0) — it stays ordinary.

— and shown on the launcher's AUDIO / DIAGNOSTICS, row Thread, in the warning color.

On a recognized handheld (an RK3326, RK3566 or H700 device tree, or a Raspberry Pi with no desktop installed) the package's install script links /etc/security/limits.d/90-sndstation.conf into place — on a desktop it does not, and says so — granting the audio group 95: what PipeWire's own 25-pw-rlimits.conf grants @pipewire, so on a machine with both it can only raise a limit, never lower PipeWire's below the 88 it asks for. pam_limits applies it at login: log out and in again, then ulimit -r should say 95. The user must be in audio (groups; sudo usermod -aG audio <user>).

Refused although ulimit -r allows it — the program says so on a second line:

rt: the limit allows 70, so the kernel is refusing it: a kernel built with CONFIG_RT_GROUP_SCHED gives a login session no realtime budget. Boot it with rt_group_sched=0 on the kernel command line.

With CONFIG_RT_GROUP_SCHED=y and cgroup v2, every cgroup but the root gets a realtime budget of zero, and a login session (/user.slice/…/session-N.scope) is never the root: realtime is refused there for everyone, root and sudo chrt included. Found on a Powkiddy RGB30 (kernel 7.0.2). Kernels with the option also take a boot parameter that switches it off, rt_group_sched=0: append it to the kernel command line — on most handheld images the APPEND line of /boot/extlinux/extlinux.conf — and reboot. cat /proc/cmdline shows it took; chrt -f 70 true from the session then succeeds. The install script checks for this kernel and says so, but leaves the boot line alone.

Where the login does not go through pam_limits, the binary can carry the capability itself: sudo setcap cap_sys_nice+ep <path to the app>. Two catches — a binary with a capability ignores LD_LIBRARY_PATH, and a rebuild drops it.

Watching it day to day: the CPU meter

The bench answers "how much more fits"; the status bar answers "how much is this using". CPU 34%, beside the battery, is the share of one core the audio thread used over the last second — the instrument or plugin, plus SDL's conversion and the ALSA write — from the kernel's clock for that thread (CLOCK_THREAD_CPUTIME_ID), which counts what the thread ran and nothing it waited for. It is the figure to watch while optimizing: a function that took the meter from 56% to 34% did exactly that.

The color follows the worst period of that second, not the average: amber once one render took 70% of its period, red at 90%. An average of 34% can hide the one block that clicks.

The same two figures are on the launcher's AUDIO / DIAGNOSTICS (row CPU) and on the --stats line (audio cpu 34% (peak 61%)). ui.cpu_meter hides the status-bar one.

To see the same thing in btop, pin the thread ("audio": { "cpu": 2 }): core 2 then carries the audio thread, and its graph reads about what the meter does — a little more, since btop also counts whatever else the kernel runs on that core. Pinning measured a step worse under heavy competition (below), which is why it is not the default; for watching, that is a fair trade.

Measured against a known load (the bench's busy-loop, SDL's dummy driver): expected 20% and 33%, the meter read 21% and 33%.

What a step is

The callback renders as usual, then spins until it has used the step's share of the period — standing in for a heavier plugin. At 70% on a 5.33 ms period, every callback takes 3.7 ms. The thread is still paced by the card (SDL's ALSA backend blocks in snd_pcm_writei), so a sustained load below 100% only underruns when the thread is woken late — which is exactly what scheduling changes are meant to fix.

The sweep stops at the first step that underran. Headroom is the last load that did not. When no step underran — the list ran out, or the run was cut short — it is printed as a floor, headroom=>=90%: nothing higher was tried.

Stopping a run early (Ctrl-C, or quitting) is fine, and on a long step the normal way to end one: the step in progress is measured as far as it got, printed under (step stopped after N s), and counted. A configuration that moves it from 60% to 85% is better by an amount that means something: that much more plugin fits.

Where "underran" comes from

Two accounts, neither of them this program's own timing:

  • alsa-lib. The stream (audio-device.md §3.0, or SDL's ALSA backend) recovers every underrun with snd_pcm_recover(…, silent = 0), and alsa-lib reports it — ALSA lib pcm.c:…:(snd_pcm_recover) underrun occurred. The bench installs alsa-lib's error handler (through the copy SDL already loaded) and counts those, still printing every message as alsa-lib would. xruns in the step line.
  • The card's buffer. /proc/asound/cardN/pcmNp/subN/status carries avail_max, how empty the buffer got; buffer_size - avail_max is the margin that was left. The kernel resets avail_max on every read of status, so with --rt-proc 1 the bench reads it four times a second and keeps the worst. margin min in the step line, in frames; 0 or less is an underrun. Off by default whenever alsa-lib's count is there, because reading status is not free of consequences: it makes the kernel ask the driver where the DMA is, and acts on the answer. On an RG CubeXX (H700, kernel 7.2) the bench counted single, sudden underruns — about one a minute, with every callback on time (worst 0.6 ms late of a 21 ms buffer) — while the same stream played for minutes without one when nothing read status. The reads are the difference, so they are off unless asked for. On the RG351V (RK3326) they never caused one. Some kernels have no such file at all: the per-stream directories are CONFIG_SND_VERBOSE_PROCFS, which the RGB30's 7.0.2 leaves off (its card1/ holds only id). There the bench says so on its first line, the RESULT line has access=unknown buffer=unknown, DIAGNOSTICS shows no buffer or margin, and alsa-lib's count is the only one.

A step is clean only when both say so. On a backend that is not ALSA (PipeWire, PulseAudio, CoreAudio on a Mac) neither exists for this stream, and a wakeup of the device more than one of its cycles late is the stand-in; the header line says which applies.

A device that takes several periods at a wakeup. Not every backend calls once a period. CoreAudio on a Mac, its device cycle 512 frames under a 256-frame stream, calls twice back to back every 11.6 ms: gaps of 0.01 and 11.6 ms, never 5.8 (measured with plain SDL, so it is the backend, not this program; asking SDL for 256-frame device buffers changed nothing). Measured against one period, every other callback looked 5.8 ms late, and a sweep "underran" at 0%. So the warm-up counts the callbacks per wakeup — burst in the RESULT line, with a line saying so when it is more than 1 — and a callback is late only by how far it trails the schedule of every one of the last burst callbacks; the stand-in above is a wakeup more than burst periods late. With a burst of 1, which ALSA's is, that is a callback's gap less one period, exactly as before, so results from before the change compare. On that Mac, with --rt-noise 4: lateness about 0.06 ms at every step, clean through 95%.

Nothing else may read the PCM's status file during a run. AUDIO / DIAGNOSTICS reads it twice a second, which is why it was once the thing to close first; it is the launcher's now and never open while an app runs, but a shell loop on /proc/asound would do the same: it resets avail_max under the bench, and on the H700 it can cause the very underrun above.

Reading the output

rtbench: load  70%  calls 3750  late p99 0.21 p99.9 0.64 max 1.90 ms  render max 0.31 ms (cpu 0.29)  margin min 180 f  xruns 0  clean
rtbench:    worst:  +3.12s 0.58 ms late (render before 0.28, cpu 0.27)  +8.11s 1.90 ms late (render before 0.25, cpu 0.24)  ...
rtbench: RESULT headroom=85% unit="Anbernic RG351V" kernel=6.12.x driver=alsa pcm=hw:0,0 access=RW_INTERLEAVED rate=48000 frames=256 burst=1 buffer=512 audio="SCHED_OTHER, nice 0, cpus 2" fifo=0 helpers_nice=0 noise=0 instrument=TESTSYNTH base_late_p999=0.64ms base_late_max=1.90ms
  • late — how far past the period each callback arrived, as percentiles; per wakeup of the device where it takes several callbacks at once (burst, above). The 0% step's figures (base_late_* in the result) are the scheduling noise floor with no load at all.
  • render max … (cpu …) — rendering alone, before the spin, as wall time and as the CPU time the thread actually got for it.
  • worst — the four latest callbacks of the step, in time order: when (seconds into the step), how late, and the callback before it — its render in wall time and in CPU time. Those two say whose fault it was:
  • cpu about equal to render, both long: the instrument's own work — a voice starting, a sample streamed. Scheduling cannot fix it.
  • render long, cpu short: the thread was preempted in the middle of rendering. Wall time alone would blame the instrument for this; it is scheduling, the same as —
  • both short: the thread was not run at all until late.

Evenly spaced times point at a periodic cause: SDL's ALSA backend re-lists the devices every 5 s from a thread of its own (SDLHotplugALSA). - over 2 ms late — every callback that late, by time (the first 32), and the median spacing between them. Four worst cases are too few to show a period; this is where a steady spacing shows up. - instrument — what was actually sounding, as the app names it: an instrument that failed to load and left a fallback playing is a different load, and the report says which. - audio — the audio thread as the kernel reports it, read back rather than assumed: policy, priority, nice, the cores it may run on. With --rt-fifo and no rtprio allowance (ulimit -r is 0) it says the raise was refused, and the run measured an ordinary thread.

Making a comparison mean something

  • Same unit, same instrument, same page, same --rt-noise. The background is part of the measurement.
  • Several runs per configuration. A single run's worst moment is partly luck. Three runs that agree are a result; one is an anecdote.
  • Change one thing at a time against a baseline run made the same day.
