The audio device layer: the mixer, the test signals, the buffer and the card

How sound gets from AudioOut to the card, and what the platform measures on the way: the hardware mixer, read and written in-process; the test signal and MDFourier; the buffer and the rate; which card plays; and where plug detection is read. The code is the SDK's audiodev, mixerio, audioout, alsastream and audiocard, and the test tone testtone.

The overview, who opens the device and when, is audio-stack.md. The unit's profile, the set-up by ear and the AUDIO page are audio-page.md; the volume and the maximums are audio-levels.md.

1. The mixer in-process, not through amixer

Every mixer and jack read, and every write, used to run amixer: about 230 ms a call on an RG351V, all of it blocking whoever waited. The page grew mechanisms to hide it — writes coalesced into a 120 ms window, reads on a worker thread, no socket polling while a test sound played, a title frozen meanwhile — and the opening freeze of the AUDIO page and of every app on a headphone plug was three or four of those calls on the UI thread.

src/mixerio.cpp does amixer's four verbs through alsa-lib instead. scontents and contents print what amixer prints (alsa-utils' show_selem and the high-level control listing, line for line), sset echoes the control as amixer does, and cset parses the value as amixer does, so the parser established against seventeen units on amixer's output stays the one reader. Checked against amixer itself on an alsa-lib control plugin answering like the handhelds' cards: both listings byte-identical, every write form the code uses landing on the same state. A read is about 0.04 ms on a desktop. Built without alsa-lib, each verb still runs amixer.

The reads still run on the poller (audiodev::poll) for the page, behind generation counters (mixerGen(), socketGen()), and poll::setSynchronous(headless) puts them on the calling thread under --shots. alsa-lib's configuration-parser noise goes through the same filter as SDL's (rt::hookAlsaErrors).

2. The test signal

AUDIO has a Test sound row, so where sound comes out and how loud can be checked without leaving for an instrument.
PINGS 180 ms enveloped sine bursts climbing in octaves, A2 to A8, 120 ms apart. The default, and the one that is safe to leave running.
SINE the steady 440 the wizard uses. Still right for "does this socket carry sound at all", still the wrong thing to walk away from.
BURSTS the pings' notes, sparser: 150 ms in every 600. The same peaks at a quarter of the heat (TestTone::Signal::Bursts).
MDFOURIER the MDFourier measurement signal, for a recorder: AUDIO's TOOLS opens its own view, which plays it once and exactly (§2.4). Not a sound to listen to, and never on the speaker.

A continuous sine at a working level is the one signal that will cook a 1-watt handheld speaker, because it is the only one with no duty cycle to hide behind — hence bursts by default and a warn color on the constant one.

Octaves rather than a sweep: the judgment is per note and a listener needs a moment on each. A small driver rolling off, a cabinet buzzing at one note, or an analog stage distorting only at the top all announce themselves in a sequence and hide in a single tone.

The steady sine sits at −12 dBFS — the reference MDFourier's sweeps and noise share — and so does everything the set-up by ear plays. The pings and bursts play at full scale where a maximum is judged (SYSTEM LEVELS, past the volume, but not on headphones) and as the main page's test sound (at the volume): an output's maximum is what a full-scale sample produces (audio-levels.md). Every constant is in milliseconds converted at the running rate, so the sequence sounds the same on a card that came back at 44100 as on one that gave 48000.

2.1 The sequence is a function of the sample clock and holds no state

m_samplePos advances by frames every callback whether the tone plays or not, so which burst is sounding, how far into it, and what the sine is doing there are all derived from the sample's number. Two runs at the same sample position are bit-identical. off == 0 gives sin(0), so every burst opens at zero by construction rather than by remembering to reset something.

The only state in the whole generator is the epoch — one integer, written in one place, when a person picks a signal.

That is what a generator with history costs. The earlier one walked a position that advanced only while the tone played and reset when it did not; any hiccup anywhere moved where it thought it was, and it sounded like the pings randomly restarting, because they did. The fix is not to chase the hiccups. It is to have nothing for a hiccup to disturb.

2.2 A lapse gaps the sound; it does not rewind the sequence

The tone is a lease: setTone() renews a 0.35 s hold and the RT side drops the tone when it lapses. The renewal is bracketed around the blocking work in the page's update(), so only the draw sits between one renewal and the next.

A lapse now leaves a hole, and the sequence carries on wherever the sample clock says when the lease is renewed — partway through a burst, if the gap cut one. A deliberate choice of signal rewinds to the bottom octave; nothing else does.

A dropped burst stays dropped rather than being replayed, which is the better answer for a test signal: a dropout you can hear as a missing ping is a dropout you know about. The page and the mixer show a dropout count beside the signal name when it is not zero, which turns "it stutters" into a number.

2.3 The fixtures

sndstation --tone-wav <pings|sine> out.wav dumps three seconds from the generator the page plays (TestTone) — not a second implementation written to check the first, which can agree with it while both are wrong. Measured that way:

7 bursts: 107 217 439 878 1756 3517 7039 Hz, 180 ms, 120 ms gaps
peak 0.2510 = -12.01 dBFS, L == R, edges in 0.0000 out 0.0001

sndstation --tone-wav mdfourier[:RATE] out.wav writes the whole MDFourier run instead (48 kHz unless a rate is given), from the run MDFOURIER plays, and checks it against the reference script's checksum: the reference file a recording is analyzed against.

sndstation --tone-wav pings-gap puts two deliberate 400 ms holes mid-sequence, because the plain dump could never catch the lapse bug: it renews the lease every block, so the failing path was unreachable. Every surviving burst still lands on its own slot at k × 0.30 s with the frequency that slot calls for:

 @0.60s slot 2  ~433 Hz  104ms   <- cut by the gap
                slot 3           <- swallowed whole: a HOLE, not a rewind
 @1.20s slot 4 ~1756 Hz  180ms   <- right slot, right note
 @2.40s slot 8  ~217 Hz  180ms

A fixture that cannot fail is not evidence. That is also where the MDFourier sequence gets checked when it arrives. test_testtone checks the same property without anyone listening: a run whose lease lapses twice must be, wherever it plays, sample for sample the run that never lapsed — and fails when the generator is made to rewind.

2.4 MDFOURIER: the measurement signal, for a recorder

MDFourier compares a recording of a known signal against the signal itself, so the samples have to reach the DAC exactly as rendered. The signal is pinobatch's mdfourier-dac, as a C++ port (src/mdfourier/, zlib) that is bit-exact with the Python original, run under the NumPy 1.x it was written for, at 44.1, 48, 88.2, 96, 176.4 and 192 kHz. Under NumPy 2 the script's pink noise overflows int16 and wraps; the port renders that reading too, on a switch (below), and src/mdfourier/README.md has the detail. MDFourierRun (include/sndstation/mdfourier.h) plays it:
The signal sync, a sine sweep and a pulse sweep from 20 Hz at 2 s an octave, white and pink noise, all at −12 dBFS; then a square wave fading from full scale (0 dBFS), and sync again. 56.4 s at 44.1 and 48 kHz, 60.4 s at 88.2 and 96, 64.4 s at 176.4 and 192.
Exact the int16 samples go to the device through AudioOut::setExact: after the app's render, in place of it; no dither, no gain, no clip. S16 is a copy and S32 the sample shifted up 16 bits. F32 is converted again after this program, so it is refused.
Once from the first sample to the last, no loop. A starts again from the top.
Underruns any one ends the run, in the audio thread, at the next block: the rest is silence and the view says where it stopped and that the recording is not valid. Counted where alsa-lib reports them (rt::alsaRecoveries); on another driver the run plays but says it was not checked.
Prepared rendered whole on a worker thread when MDFourier is chosen, at the running rate: a few hundred milliseconds and 5 MB at 48 kHz, 22 MB at 192 kHz, given back when the page closes. The audio thread only copies.

The view (launcher/audiomdf.cpp) shows the rate to record at in large type, with what the device is handed and what the card runs, and refuses to start, saying why, when:

  • the rate is not one of the six (choose one in Sample rate);
  • the card runs at another rate, i.e. ALSA is resampling;
  • the output format is f32;
  • the sound is going to the speaker (a USB card has none; on a desktop the system decides).

The first start each time the page is opened asks once: full scale at the end, line output to a recorder, nobody's headphones. While it plays the page forks nothing (no amixer reads, as for the test tones), and the run ends if the device under it changes (a card plugged in, a rate or size moved): that is a gap the recorder heard. B stops it; leaving the page does too.

A run that completes says so, and that it had no underruns; the recording is then the one to analyze, at the rate shown.

The reference file. Preparing the run also writes the whole signal as a 16-bit .wav on the unit, for the recording to be compared with, and the view shows where and whether it is there:

~/.local/share/sndstation/mdfourier/mdfourier-dac-48000-numpy1.wav

($XDG_DATA_HOME/sndstation/mdfourier/ when that is set.) One file per rate and NumPy reading, written once, on the worker, to a temporary name and renamed, so a file under the name is always whole; a later prepare finds it and leaves it. It is the very render the run plays (test_mdfourier reads one back and checks it against the script's checksum), so scp it off, or pull the card. sndstation --tone-wav mdfourier[:RATE][:numpy2] out.wav writes the same file on a desk.

Which NumPy. system.json's audio.mdfourier_numpy picks how the script is read, which decides the pink noise and nothing else:
1 (default) NumPy 1.x, what the script was written for: its pink mixer's sum promotes to int64 and never overflows.
2 NumPy 2: the sum stays int16 and wraps; a quarter of the pink noise differs. For matching a reference rendered from the script on a current NumPy.

Read when the page opens; the view names the one in force on its REFERENCE line, and the file is named for it.

The checks: test_mdfourier plays every rate, both readings, through the run in uneven blocks and compares with the reference checksums, writes and reads back a reference file, and checks an underrun's stop; test_mdfourier_ref renders each rate with the Python original (tests/reference/, needs numpy) and cmps the files, for NumPy 1.x's reading and, where NumPy 2 is installed, for NumPy 2's; test_audiosetup opens the view on SDL's disk device and finds the reference file where the view says, for each value of the switch; test_audioout plays a whole run through SDL's disk driver at S16 and at S32, with dither on and the app rendering underneath, and checks what the device was handed.

3. What can and cannot be set about the buffer
period size ours, from the page. Buffer size changes it live. On the stream run here (§3.0) it is the period asked of alsa-lib; on SDL's stream it becomes SDL's samples, which becomes ALSA's period. It is saved in the unit's audio.json: one size for the built-in outputs, and its own for a USB or HDMI card (audio-page.md). audio.buffer_frames in system.json is only the default a unit has not changed.
period count two, or the fewest the card allows: the low-latency answer. Every other value adds latency.
start threshold ours (§3.0): the whole buffer, at the first start and after every underrun.
sample rate ours, from the page. Sample rate changes it live (§3.2), saved in the unit's audio.json beside the period size; 0 is Default. audio.sample_rate in system.json is only the default a unit has not changed.
format, access negotiated. A device may hand back something near what was asked, and nothing says so unless /proc/asound is read.

3.0 The stream is run here, on alsa-lib

On Linux nothing is played through SDL: src/alsastream.cpp opens the device with alsa-lib and runs the writer thread itself, whichever device it is — the card this program chose, AUDIODEV or alsa_pcm as given, or default and whatever the system put behind it (a plug, a dmix, a sound server's ALSA plugin, so a server is reached as aplay reaches it). SDL's audio is started on its ALSA driver for that, whatever it would pick first (a sound server's), and only lists the devices for the log: SDL_AUDIODRIVER is set for that one call and taken away again, so nothing the program starts inherits it. SDL's stream is left for where there is no alsa-lib (macOS, Windows, a build without it), and for an SDL_AUDIODRIVER set outside, as the tests' disk driver is. The log says which: "the stream run here, on alsa-lib", or why not.

The reason is the start threshold. SDL's backend sets it to one frame, so a stream starts, and starts again after an underrun, with one frame queued. At a short period that misses the next deadline at once: one underrun becomes thousands a second, each a stop and restart of the card's DMA. On an H700 under PREEMPT_RT that storm is a kernel panic (sun6i_dma_interrupt, racing a stop), while aplay, which fills the whole buffer before it starts again, came through 200 forced underruns at 32 frames on the same kernel without a mark.

So the stream does what aplay does:

  • start threshold = the buffer: nothing plays until the buffer is full, at the first start and after every underrun;
  • an underrun is recovered with snd_pcm_recover (prepared again, then refilled), which also reports it, so the click count on DIAGNOSTICS is the same;
  • the writer blocks in snd_pcm_writei, as aplay and SDL do: the kernel waits for exactly the frames still to be written. A non-blocking writer that waits with snd_pcm_wait does not work: a write takes the few frames free between two interrupts, the writes stop lining up with the card's periods, and the wait (for a whole period free) wakes an interrupt late to a buffer nearly empty — on an RK3326 at 256 frames, periods in pairs, no safety margin, underruns by the thousand. A card that stops taking anything is the kernel's to notice (an I/O error after its timeout, deviceStopped); closing drops the stream first, so it never waits on the card.

SNDSTATION_AUDIO_STREAM=sdl (or sndstation-audiotest --sdl) puts SDL's stream back on the same device, to compare: a developer's switch, said in the log at every open. Each underrun on our stream is said in the log, for the first five then every hundred: whether the writer was late (more time since its last write than that write left queued) or the card ran dry with audio still queued.

The callback is the same one SDL called: the same conversion, metering, timing and realtime raise; a change the callback reads (setExact) is made under the stream's fill lock instead of SDL's device lock.

3.1 The sizes offered are the sizes the device gave

How finely the period can be set is a property of the driver and the hardware, and none of it can be looked up:

  • SDL's ALSA backend asks for the period nearest the request, and the card decides: a codec can round to multiples of 16 or 64, and a dmix default device runs at its own fixed size whatever is asked.
  • PipeWire has a floor (32 frames at 48 kHz); PulseAudio takes anything.
  • Every other SDL2 backend (dummy, jack, sndio, OSS) takes powers of two only, and asking one of them for anything else is not merely rounded: SDL 2.26–2.32 computes the buffer size before rounding and never recomputes it, so the callback is handed a buffer sized for 48 frames and told it holds 64. A heap overflow — reproduced with plain SDL on the dummy backend, free(): invalid pointer on close. Only alsa, pulseaudio, pipewire and disk set SupportsNonPow2Samples; on anything else sndstation asks for powers of two only, at startup as well (a buffer_frames of 1000 in system.json used to reach that bug).

So the first press on Buffer size asks: the running device is closed, fifteen sizes — the powers of two from 32 to 4096 and the halfway points between them, or just the powers of two where those are all it is safe to ask — are each opened paused and closed again, and the distinct sizes that came back become the choices. A device that rounds to multiples of 64 offers those; a dmix that only runs at 1024 offers one size and says so. The help box lists them. It is a moment of silence, so the page says "Asking the device…" in the frame before it happens, and it is done once a session.

Each change after that is a reopen at the new size, at the rate already running (SDL_AUDIO_ALLOW_FREQUENCY_CHANGE is not passed, so a device that comes back at another rate is resampled rather than detuning the engine and the plugin). Steps are applied after 0.45 s without a press, so holding the d-pad costs one gap, not one per step. The callback takes whatever frame count it is handed and the plugin path slices to the block the plugin was activated with, so nothing downstream has to be rebuilt. The timing counters reset on a reopen, which makes the row's "no clicks / N clicks" a verdict on the size on screen.

3.2 The rate: Default first, then what the device gave

SDL2 has no call that lists a device's rates, so they are found the same way as the buffer sizes: on the first press the running device is closed, the common rates (22.05, 32, 44.1, 48, 88.2, 96 and 192 kHz, plus whatever Default resolves to) are each opened with the rate allowed to move, and the distinct rates that came back are the choices. ALSA's plug layer and the sound servers resample and so take all of them; a raw hw: device offers its own; a dmix offers one.

Default comes first, and is what ships (sample_rate: 0). It is not SDL's default — asked for a rate of zero, SDL picks 22050 — but the device's own rate where SDL can report one, which only the PipeWire and PulseAudio backends do (SDL_GetDefaultAudioInfo), so nothing is converted between the program and the server. Everywhere else, ALSA included, it is 48 kHz: the rate the program always asked for before. It stays a separate choice even when it resolves to a number also in the list, because it is a different promise — "whatever this device prefers" follows the device; 48 kHz picked by number stays 48 kHz.

A change of rate is a reopen at the new rate with the buffer size kept. On the page that is the whole of it — it plays nothing but its tone. An app that changes rate while running (AudioOut::setRate) hears about it in its rate callback while the device is still paused, and re-prepares everything that turned the old rate into a constant: clocks, synths, a hosted plugin (deactivated and activated again at the new rate, which keeps its patch where a reload would lose it). Voices already sounding are best released, having been started at the old rate. AudioOut::sampleRate() returns the running rate, not the one asked for, which a device allowed to move it could make wrong.

Measured through the real callback on SDL's disk backend: the test sine reads 440.00 Hz at 22.05, 44.1, 48 and 96 kHz after every sequence of changes tried, at -12 dBFS throughout.

Which is why DIAGNOSTICS prints ASKED FOR and GOT on adjacent lines. The numbers come from /proc/asound/cardN/pcmNp/subN/hw_params and status — no device is opened to ask, so nothing is disturbed, and the stream is found by looking for the one that is not closed, on whichever card it turned out to be.

The row worth watching is WORST MARGIN: buffer_size - avail_max. avail_max is the high-water mark of how empty the buffer ever got, so this is the distance from an xrun the run has actually survived, as opposed to the nominal figure. It turns warn-colored below one period, which is one late wakeup from a dropout.

DIAGNOSTICS also measures the callback itself — gap, render time, and a count of late arrivals (>1.5 periods) — with SDL_GetPerformanceCounter, which is a vDSO read and safe from a callback.

What it calls a click, there and on the Buffer size row, is an underrun as alsa-lib reports it: the stream (§3.0, or SDL's ALSA backend) recovers every one with snd_pcm_recover, which reports it, and the program counts those reports for the whole run (rt::alsaRecoveries). Late callbacks are kept as their own row and are not the same thing: a Powkiddy RGB30 (RK3566) delivers its callbacks in pairs — two together, then a double gap — and scored 1100 "late" in a ping test that underran about 10 times. Where alsa-lib cannot say (not ALSA), late callbacks are the only stand-in, and the page says "likely".

The same handler is installed before SDL starts its audio (so it also catches SDL's first device listing), and it hides alsa-lib's configuration-parser messages: everything from its conf.c and confmisc.c. SDL lists every device at startup and again every five seconds, and alsa-lib tries each standard definition (hdmi, surround, iec958…) against every card, complaining about each that does not fit: a two-card RGB30 printed dozens of Unknown parameter CARD a scan, none about anything playing. One line says they are hidden; SNDSTATION_ALSA_VERBOSE=1 shows them, for debugging an asound.conf of one's own. Everything else alsa-lib says, underrun occurred included, prints as before.

Raise Buffer size first if it reports underruns. 512 doubles the margin and costs 5 ms; on a box where the UI, Mesa and a forked amixer all compete for four cores, that is usually the difference between clicking and not.

The audio thread runs SCHED_FIFO 70 (audio.realtime_priority; 0 = an ordinary thread), raised by the thread itself on its first callback, and may be pinned to a core (audio.cpu). It needs an rtprio allowance, which the package grants the audio group on a handheld; without one the raise is refused and DIAGNOSTICS shows the thread as ordinary, in the warning color. What it changes was measured, not assumed: see rt-bench.md.

3.3 Which ALSA device: the card itself, not default

sndstation opens hw:<card>,0 rather than default. The stream run here (§3.0) opens the device it is named; for SDL, which reads AUDIODEV at every open, the same name is set there after the audio subsystem is up and before the first open, so a probe or a reopen through SDL uses the same device.

The variable belongs to the process, and every program it starts inherits it. So the last AudioOut to close puts it back as the process found it: unset, or what was set outside. An app the launcher starts afterward chooses its card by the rule below, as it would started from a shell, rather than taking the launcher's choice for a user's (rule 1), and playing through SDL's own ALSA stream instead of its own.

default on a system with no ALSA configuration is alsa-lib's plug over that same card. It offers nothing to share — there is no dmix in it — and plug drives the card through MMAP. On an RG351V (RK3326, mainline 6.12 and 7.1) that path underran steadily at 48 kHz / 256 frames with the built-in synth alone, at a few percent CPU, under SCHED_FIFO 80 as well. Opened as hw:0,0 the same program was clean. hw_params under both showed the same rate, format (S32_LE), period (256) and buffer (512); the only difference was access: MMAP_INTERLEAVED through plug, RW_INTERLEAVED from SDL's own snd_pcm_writei on hw. The samples arrive already in an integer format (§3.4), so nothing is lost by skipping plug, and the AUDIO page's rates and sizes become the card's real ones.

The rule, in order:

  1. AUDIODEV set in the environment — used as given.
  2. audio.alsa_pcm in system.json, if not empty — used as given, "default" included.
  3. Plays on names a card (USB or HDMI) that is plugged in — that card. Not plugged in, Automatic until it is. Plays on one of the built-in card's outputs takes the built-in card (rule 6) whatever is plugged in.
  4. Plays on is Automatic (the default) and a USB card that plays is plugged in — that card. Someone plugged it in to hear it.
  5. This system configures ALSA (/etc/asound.conf, ~/.asoundrc, $XDG_CONFIG_HOME/alsa/asoundrc, a non-empty /etc/alsa/conf.d or /usr/share/alsa/alsa.conf.d) — default. Somebody may have put dmix, softvol or a sound server behind it on purpose.
  6. Otherwise hw:CARD=<id>,DEV=0: the card named by ALSA_PCM_CARD or ALSA_CARD if one is set, else the first card that is not a display output (HDMI, DisplayPort, S/PDIF), named by its id so a change in probe order cannot move it. Not card 0: on a Powkiddy RGB30 (RK3566) card 0 is HDMI and the speaker codec is card 1, and "card 0" played to a cable nobody had plugged in. Nor a virtual card: on an H700 image that loads snd-aloop, card 0 is ALSA's Loopback, which plays into nothing. ALSA has no word for "real hardware"; sysfs does. A real card's device (/sys/class/sound/cardN/device) hangs off a bus (USB, PCI, an SoC's) or has a firmware node (of_node from the device tree, firmware_node from ACPI); a made-up one is a platform device straight under /sys/devices/platform with neither (snd_aloop.0, snd_dummy.0, snd_virmidi.0). Where sysfs cannot say, the driver's name does (Loopback, Dummy, VirMIDI). A virtual card is taken only when named, or when there is no hardware at all. With nothing but display outputs, the first of them.

A card picked by rule 3 or 4 that will not open (busy, or a USB card whose /dev/snd node udev has not finished with) falls back to the built-in card, and is tried again two seconds later. A device picked by rule 2, 3, 4 or 6 that still will not open gets one retry on default, so a wrong guess costs the log a line, not the program its sound. The log says which device was used and why.

USB cards say what they take. /proc/asound/cardN/stream0 lists every format and rate of a USB card's endpoints, and src/audiocard.cpp reads it (nothing is opened to ask). Two things follow from it:

  • Format. SDL2 has no 24-bit packed format. A card that offers none SDL knows — a Dirtywave M8 takes S24_3LE and nothing else — cannot be opened on hw at all ("Couldn't find any hardware audio formats"), so it is opened as plughw:CARD=<id>,DEV=0 and handed s32 (an s16 setting would drop eight bits that plug then pads back). Plug's conversion from S32 to S24_3LE is a truncation of bits the DAC never had. A card that takes any SDL format stays on hw.
  • Rate. "Default" is 48000 when the card takes it, else the card's own (the M8's 44100), and a pinned rate the card does not take is replaced the same way. Through plughw anything would open — resampled by alsa-lib's linear converter — so setRate and the AUDIO page's rate list are held to what the card lists.

The log then says what the card actually runs at, from its hw_params: audio: card M8 runs S24_3LE, 2 ch, 44100 Hz (plughw converts from S32). AudioOut::cardFormat() and cardRate() carry the same.

Hotplug. An app calls AudioOut::service() once a frame. A device SDL marks stopped (a USB card pulled mid-period: the write returns ENODEV and SDL gives the device up) is noticed at once, and /proc/asound/cards is read twice a second. When the card rule 3 or 4 would choose differs from the one playing, the device is closed and opened on the new one; a rate that moved goes to the app's RateFn with the device paused, the same as a rate change from the AUDIO page. Only a PCM this program chose is moved: rules 1 and 2 are left alone.

A USB card's own volume. Many come up with their playback level at the bottom, so the first time a USB card is played to, a PCM or Master playback level at 0% is raised to 50%, once. (On a real M8 set to 0% this raised PCM to 128 of 255; the M8 then kept 50% across a cable pull and replug. The M8 has two controls both named PCM, and only the first, 'PCM',0, is reached.) The unit's audio.json records it under the card's endpoint (usb:<vendor>:<product>, "raised": true), and a card with that record is never touched again on this unit: a level turned down afterward stays down. No other level is touched; a USB interface's other playback levels are often input monitoring.

More than two channels. The stream file lists each endpoint's channel count (Channels: 24). audiocard keeps them per direction (Card::channels, Card::capChannels), and CARDS shows them: Plays S24_3LE 2 ch 44.1 kHz · Records S24_3LE 24 ch 44.1 kHz. AudioOut plays stereo and asks for 2 channels, so a card whose playback is 2 channels is used exactly as before. sndstation does not record; a card's capture channels are listed for the person choosing, and an app that records opens them itself (hw:CARD=M8,DEV=0, all channels at once).

A Dirtywave M8 in its multichannel USB mode (SYSTEM → USB AUDIO MODE, firmware 6.5.0 and later) is that case. It still plays 2 channels, and records 24. Dirtywave's channel order is:

Channels What
1–2 main mix
3–18 tracks 1–8, a stereo pair each
19–20 mod FX
21–22 delay
23–24 reverb

Switch the mode, then unplug and replug the M8 so the kernel reads the new endpoints. In this mode the M8 is a different USB product, 16c0:048b (stereo mode is 16c0:048a), so audio.json keeps a separate first-sight record for it. Its 'PCM',0 then has eight channels: front left and right at 50%, the other six at 0%. The volume raise looks at the first channel, so it leaves them alone.

Measured on the SP (2026-10-17), with a song playing on the M8 and AudioOut playing a 440 Hz tone to it at about -14 dBFS:

  • Playback: plughw, S24_3LE, 44.1 kHz, 0 xruns.
  • Recording: all 24 channels carry the song, and each track's pair reads the same on both sides.
  • main: -7 dBFS peak
  • tracks: -15 to -27
  • mod FX, delay, reverb: -38 to -42
  • InputMeter: reading the same channels, it agreed to within a dB.
  • Our tone: it was not in the recorded main mix (440 Hz at -66 dB): what the M8 receives over USB does not come back in its multichannel capture, or its USB-input level was down.
  • USB I/O view: on the SP with the M8 plugged in, it names the card and its formats and labels the meters MAIN, T1–T8, MOD, DLY, REV.

--fake-audio m8multi answers as the SP with the M8 in this mode.

A card that plays more than 2 channels and not 2 (an 8-out interface with no stereo altset) has not been tried: hw would refuse SDL's 2 channels, and plughw's channel routing has not been measured.

3.4 What the device is handed, and where it clips

Everything up to the device is float: the engine, the internal synths, a hosted plugin, the host hooks. Full scale is ±1.0, and something has to decide what happens to a sample past it. The internal synths never get there — their limiter (limiter.h) bends to a ceiling of 1.0 — but a plugin, the hooks and the click are summed in unlimited, on purpose.

audio.output_format (--audio-format for one run) says who converts:

converted by an over
s16 (shipped) this program, AudioOut::toDevice (SDK) clipped flat here
s32 this program clipped flat here
f32 alsa-lib's plug, or a sound server (SDL, on SDL's stream) the converter clips it; a server may turn it down first

With s16/s32 the clip happens in the loop that counts it, so the count means the same on every driver: through PipeWire or PulseAudio an over is no longer quietly rescued by the server's own volume. SDL 2.32's own F32→S16/S32 converters saturate too (SDL_audiotypecvt.c), so on ALSA hw f32 clips at the same place — just out of sight. The device is opened without SDL_AUDIO_ALLOW_FORMAT_CHANGE, so SDL delivers exactly the asked format; on a card that wants another integer width it widens S16 losslessly.

s16 is dithered (audio.dither): two uniform draws a sample, differenced — one step of triangular noise, from a xorshift32 — which turns 16-bit rounding's low-level distortion into a steady hiss about 90 dB down. s32 is not; its step is far below any DAC's.

The same loop measures the peak for the HUD ladder and counts the overs: the square at the top right of the ladder lights red for two seconds after any block went over, and AUDIO / DIAGNOSTICS says how many and how far (Clipped: 37 blocks · worst +1.8 dB over full scale), beside what the device is handed (Samples). NaN is not looked for: a plugin that outputs it is broken, and the check would cost every sample.

Checked through SDL's disk driver, which writes what the device is handed: the same chord in all three formats measured peak 0.3212 and RMS 0.0763-0.0764 once scaled back.

3.5 With no device: the app's own clock

A headless run, or one where no device would open, has no callback. The app calls AudioOut::pumpManual(dt) from its own loop instead, with the seconds since the last call, and the render function runs as the callback would have run it: the volume, setExact's samples and the peak meter included. With a device running it does nothing.

dt seconds is rarely a whole number of samples. At 48 kHz a 60 Hz loop is 800 a frame, but a 144 Hz one is 333.33…, and a loop pumped in small steps may be owed less than one sample a call. So the fraction left over is carried to the next call rather than dropped. Dropped, the 144 Hz clock would run a third of a sample slow every frame, and a small enough step would never render anything at all. Carried, the samples rendered over a run match the time that passed, to within one.

A call renders at most 4096 frames. What a long stall is owed beyond that is dropped, not carried: the run's clock loses that time rather than catching up in a burst. A dt that is zero, negative or not finite is ignored. The carry starts again at each open().

3.6 Opening and closing: the fades

A stream started at full level, or cut there, is a step, and a speaker plays a step as a click. So the sound comes in from silence over AudioOut::FADE_MS (5 ms, 240 frames at 48 kHz) after every start, and goes out over the same before every close, reopen(), setRate(), rate or size probe, and card move. The gain is applied in the callback after the volume and before the conversion, so the meter and the over count see what the device gets.

A fade out is played, not just computed: close() and the rest wait until the gain is at 0 and three whole callbacks have gone out silent, by when whatever the device still held of the slope has played too (two periods of buffer, and one more). That costs a close about three periods and the fade; it waits at most 100 ms past that for a callback that never comes. A device not started, stopped or playing the exact path (setExact, MDFourier) is closed at once: there is nothing to fade, and the exact path's samples are never touched. The destructor does not wait either: the app the render function belongs to may already be going, so an app that wants the fade calls close().

What a fade cannot remove is what the hardware does when a device opens or closes: a codec that powers its output down some seconds after the close (ASoC's pmdown_time, 5 s by default; a late pop on some H700 units) still clicks then. Keeping the device open is the remedy for that, not the fade.

test_audioout reads what the device was handed (SDL's disk driver): the slope in and out, each about 240 frames, no step larger than a slope's, and the silence before the close.

4. Where plug detection is read: four doors

audiodev::readSocket() answers "is something in the headphone socket?" There is no one place a Linux handheld says so, so it tries every door, keeps what each one said in Socket::scanned, and takes the first usable one in this order of confidence:

kind door why it is where it is in the order
alsa the card's read-only BOOLEAN jack kcontrols (amixer contents) set by the same driver that decides where the audio goes
input evdev nodes with SW_HEADPHONE_INSERT, SW_LINEOUT_INSERT, SW_MICROPHONE_INSERT or SW_JACK_PHYSICAL_INSERT a copy of the codec's state, and on some clones a copy that was never wired up
extcon /sys/class/extcon older vendor kernels
switch /sys/class/switch (Android's switch class) older vendor kernels still

The input door is read through device events: readSocket() opens a one-shot DeviceEvents scan of /dev/input, with no hotplug watch and no hallkey door, and audiodev::inputSockets() turns its rows into SocketSources. That leaves one evdev switch reader in the SDK. Each node that carries a jack switch becomes a row like HEADPHONE=1 MIC=0, listing every jack switch it has with its state. A node whose HEADPHONE bit never moves while its LINEOUT bit does is a diagnosis, and only the full list shows it. A node with only LINEOUT or JACK is still offered. A node that couldn't be opened is kept with its error, so "denied: join group 'input'" can be said instead of "no jack found". Nodes with no jack switch are left out.

--fake-audio snapshots answer from the ALSA door alone, so they never reach this one. inputSockets() is public so it can be tested on rows instead of a unit, in tests/test_deviceevents.cpp.
