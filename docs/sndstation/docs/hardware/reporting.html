Reporting a hardware result

Draft for #172. Placeholders marked TODO(#236/#…) wait on a decision. #236 tracks each one, and the second number is the decision's closed issue.

A private-beta slot holder measures what the unit's issue says it "must show" and reports it. This page says what to collect, how to get it, and where it goes. The slots and their "must show" lines are in supported.md.

What to collect

Item Where it comes from
Unit the model on the case, and the slot number from supported.md
SoC the CPU row on the launcher's ABOUT page, for example "Rockchip RK3326"
Image which image the unit runs: the sndstation rootfs, ROCKNIX, or a stock BSP image (images.md), and its name or date. TODO(#236/#124): how an image states its own version
Version the platform's version, on ABOUT
Unit id the SOC ID row on ABOUT, for example RK3326-URKC08010-4FE23CAAD163F02F
--rt-bench output the RESULT line and the step lines above it, or why you could not run it
What the slot's "must show" says one line each: shown, not shown, or could not be tried
Config files ~/.config/sndstation/gamepads.json once Map this controller saves it, and the rings entry --led-slots prints

Copy the SOC ID exactly. It is the key under which audio.json, leds.json, and deviceevents.json file a unit (unit-identity.md). Two units of one model have different ids.

How to get each

The unit id and version

Open the launcher. L1 and R1 (or left and right) change the page: APPS, PLUGINS, SETTINGS, ABOUT. ABOUT lists the platform's version, the board, the SOC ID, the kernel, the CPU, memory, uptime, SDL, the display, the input device, and the audio settings. It is read-only; B leaves (launcher.md, About).

The launcher also prints the id on a unit: line and the chip on a soc: line. Under sndstation-session, those lines go to ~/.local/state/sndstation/session.log, and the session before this one is in session.log.1. With SNDSTATION_SESSION_LOG=-, or with the launcher run by hand, they print on the terminal.

grep -E '^(unit|soc):' ~/.local/state/sndstation/session.log

--rt-bench

The bench belongs to the SDK, and an app runs it: the app opens its AudioOut, calls rtbench::start(), and parses the --rt-* flags (rt-bench.md, "Running it"). The example app does: hello --rt-bench (#194, examples/hello). The .deb does not install hello, so build it or copy it to the unit. The launcher does not take the flag.

hello --rt-bench --rt-noise 4

Run it on the unit itself, not on a desktop, and report the whole output: the RESULT line carries the unit, kernel, driver, PCM, rate, frames, and buffer. Several runs that agree are a result; one is an anecdote. If the audio thread is refused realtime, the bench says so on stderr, with the cause (rt-bench.md, "Allowing it"); include that. Sound routes (rk817 and h616 units)

Open the Audio page and use an output's Set up by ear. Answers are kept when the DONE screen says SAVE, into ~/.config/sndstation/audio.json under the unit's id (launcher.md, Audio). Report what each route did, and whether it survived a headphone plug.

Buttons and layout

SETTINGS → Controls has Test buttons, which shows the map end to end with the raw SDL source, and Map this controller, the wizard. The wizard saves into ~/.config/sndstation/gamepads.json (launcher.md, Controls). Send that file. For a layout, the rules for placing controls are in gamepad-layout.md.

Stick lights

sndstation --led-slots    # measure: every wire slot, one at a time
sndstation --led-test     # check: each logical LED in turn

--led-slots asks for a clock position per slot and prints the rings entry to paste. --led-test walks both rings clockwise: N, NE, E, and so on (stick-leds.md, "Checking a unit"). The user has to be in dialout.

The lid (RG35XX SP)

On the sndstation rootfs, close the lid, open it again, and say whether the unit reacts as the lid policy says. On a stock BSP image, read the hallkey attribute under /sys/class/power_supply (the node is axp2202-battery) with the lid open and then shut, and report both values (device-events.md, "hallkey").

File the report

Open a "Hardware report" issue: the template is .github/ISSUE_TEMPLATE/hardware-report.yml. Fill in what is asked, and attach the output rather than describing it. The unit's own issue (#126 to #133) ticks its gap boxes as results land: TODO(#236/#125) whether the reporter or a maintainer links the report there.

Where results land

#125 sets where each result ends up, so that each "must show" changes the file it concerns:

Result File
--rt-bench RESULT rt-bench.md
unit id, same-lot collisions unit-identity.md
button maps, layouts config/gamepads.json
stick-light rings stick-leds.md, config/leds.json
the lid's hallkey config/deviceevents.json
