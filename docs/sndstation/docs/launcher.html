The sndstation launcher and session

sndstation is the first thing on screen once the OS is up. It lists the installed apps and starts the one you pick. sndstation-session runs it in a loop: when the app exits, the launcher comes back. "Exit to shell" ends the loop. Both ship in the sndstation package and are built from sndstation/launcher/ and sndstation/session/ on the public SDK alone.

How an app is started

The launcher replaces itself with the app. It shuts SDL down (display, joystick, audio) and then execs the app's program. So:

  • the app gets all of the memory and every device;
  • an app that crashes leaves no launcher half-alive behind it;
  • the session loop, not the launcher, is what brings the list back.

The app runs with SNDSTATION_SESSION=1 in its environment. An app may use it to say "back" rather than "quit".

Which platform is installed is in a file, not the environment: /usr/share/sndstation/version holds its version on one line (0.17.1). The package ships it, so any program can read it, started by the launcher or not, and it is never out of date after an upgrade.

Listing an app: the manifest

One file per app, <id>.json, in any of these directories (later ones override earlier ones with the same id):

directory who puts it there
/usr/share/sndstation/apps the app's package
~/.local/share/sndstation/apps you: your own entries, or overrides
$SNDSTATION_APPS (colon-separated), --apps DIR development 
{
  "name":        "Example",                         // required
  "description": "What it is, in a line",
  "exec":        ["/opt/example/example"],          // required: argv, no shell
  "order":       10,                                // optional, low first
  "skin":        "system"                           // optional: wear the unit's skin
}

  • skin: "system" starts the app in the skin chosen in Display (below), a skin's id in that one. The launcher hands it over as SNDSTATION_SKIN; the app's own style goes over it. Without it, an app has its own look (sdk-style.md).

  • exec runs as given: no shell, and an absolute path is not looked up on $PATH.

  • A program that is not there (or not executable) is still listed, grayed out with the reason. A broken install says so instead of vanishing.
  • Only apps with a manifest are listed. A manifest without name or exec is skipped, with a line on stderr.
  • The list is read when the launcher starts, and the launcher is a new process after every app, so coming back from one always reads it afresh. For something installed or removed while the launcher sat on the list (a port added over SSH, say), X (North) rescans. Nothing reads it on a timer: the unit is an audio device, and an idle launcher does nothing but keep its sound stream, which the screensaver lets go of. Starting an app reads the list once more first, so one removed a moment ago is not started, and neither is whatever the cursor lands on in its place.

An app's package installs its manifest into /usr/share/sndstation/apps.

The session

sndstation-session loops on the launcher. What each run returns says how it ended:

exit means the session
87 "Exit to shell" ends; the shell that ran it carries on
anything else the app, or the launcher, ended starts the launcher again

Three failing runs in a row, each under five seconds, also end the session. That catches a launcher that cannot start (no display, a broken install), which would otherwise flicker forever. The session says so and leaves you a shell.

Arguments are passed to every launcher run. SNDSTATION_LAUNCHER overrides which program it runs.

Booting into it

On a handheld, the sndstation package sets this up when it installs, as part of the handheld half it already links into /etc (the realtime allowance, the LED rule). The unit's own screen then boots into the launcher:

  • /etc/profile.d/sndstation-session.sh is linked to sndstation/session/profile.sh. A login on tty1 runs sndstation-session, once. SSH, a serial console or any other terminal is an ordinary shell. Because it is a real login, pam_limits applies, so the audio thread gets its realtime allowance.
  • /etc/systemd/system/getty@tty1.service.d/sndstation-autologin.conf is written to log tty1 in automatically. It names a user, so it is written rather than shipped, and it carries a marker line so the package only ever removes its own.
  • /etc/systemd/system/sndstation-lid.service applies the lid policy, system.json's "system": {"lid"}, to logind at boot. It writes /etc/systemd/logind.conf.d/sndstation-lid.conf from the tty1 user's setting, so a change takes effect from the next boot. See device-events.md.
  • "Exit to shell" ends the session, and that login carries on to a normal prompt. Logging out of the prompt logs in again, and the launcher comes back.

Whose login it is: SNDSTATION_USER if given at install time, else whoever ran sudo, else the first ordinary account (uid 1000 and up, with a shell). The script says which, and says if that user is missing from audio, video or input.

Nothing changes until the next boot: the install never restarts tty1 under whoever is using it. Nobody's ~/.profile is edited.

at install time
SNDSTATION_BOOT=no leave tty1 alone, and remove what an earlier install set up. Remembered (/etc/sndstation/boot) through upgrades, until…
SNDSTATION_BOOT=yes …this turns it back on
SNDSTATION_USER=<name> log this user in
SNDSTATION_SYSTEM=no no handheld half at all (this included)

An autologin drop-in of the same name that the package did not write is left alone, and the script says so. Without systemd, the profile link is still made; logging the user in on tty1 is then up to the image. Removing the package removes both. Purging it also forgets the yes/no.

Bluetooth at boot

The RG35XX SP and the other H700 units with a Realtek RTL8821CS have their Bluetooth on a UART, spoken to over the Three-wire (H5) protocol. On about half of all boots the chip never answers the link's SYNC. The driver binds and logs nothing more; no hci0 appears, so bluetoothd never starts, and paired controllers (a BLE-MIDI keyboard, say) stay away until a lucky boot. Measured on an SP (Debian 13, kernel 7.2): 4 boots of 8 came up this way. Rebinding the driver powers the chip down and up through its enable GPIO, and it then answers at once.

The handheld half does that for you: /etc/systemd/system/sndstation-bt-h5.service is linked to sndstation/system/sndstation-bt-h5.service and enabled. At boot it runs /usr/share/sndstation/system/sndstation-bt-h5, which waits for each device the hci_uart_h5 driver has bound and, if no hci device appears within six seconds, rebinds it, up to three times. When hci0 registers, udev starts bluetoothd as usual. A unit without an H5 controller finds none and the service exits. What it did is in journalctl -u sndstation-bt-h5.

By hand, as root, the same thing is:

echo serial0-0 > /sys/bus/serial/drivers/hci_uart_h5/unbind
echo serial0-0 > /sys/bus/serial/drivers/hci_uart_h5/bind

On a desktop none of this happens. To try the session there, run sndstation-session by hand.

Controls

SETTINGS → Controls sets up the unit's gamepad for every app (launcher/controls.cpp):
Test buttons press anything: its pill lights. The map, end to end, with the raw SDL source and every axis live. START three times leaves.
Map this controller the wizard. Each control is haloed in turn; press its button twice to confirm, hold any button 1.5 s to skip it (or keep what it was), and a hat d-pad is taken whole. It edits the pad's existing entry rather than relearning it, and saves into ~/.config/sndstation/gamepads.json, live at once.
Calibrate sticks ranges (swirl both sticks), swapping the two sticks (units of one model wire them either way round), and per-stick inversion and X/Y swap, into calibration.json

The wizard reads raw button numbers, not the pad's logical bits: an unknown pad runs on the generic fallback map, whose bits are guesses.

One pad is in use at a time: the first one SDL reports. Another pad plugged in alongside is ignored entirely, buttons, hat and sticks, until the one in use is unplugged; then the next one still connected takes over, on its own map and calibration. (Its presses used to be read through the first pad's map.)

Key
A or START pause the log, or resume it. Lights and counts carry on while it is paused
X clear the log and the counts
Y hide or show timing clock and active sensing. Hidden by default
UP / DOWN, L1 / R1 scroll back a line or ten (pauses), and forward again
B back to the Controls menu

On a desktop's keyboard: A is Z or A, START is Return, X is Space or C, Y is V, L1 and R1 are 1 and 4, and B is X or D.

No gamepad at all

Before anything else, after the boot logo (the session's first launcher) or on a handheld's screen: with no gamepad half a second in, the launcher says "No gamepad found" and counts five seconds down, then leaves to the shell (exit 87, as Exit to shell), where a keyboard or ssh can find out why: a driver that failed, a device tree without the pad. A pad that arrives meanwhile, or any key on a keyboard, ends it and the launcher carries on, the pad's own first run next. A launcher started by hand on a desktop has the keyboard, and never shows it.

First run

When the unit's pad is not in the gamepad database, Controls opens by itself before the list, on a card:

  • press any button twice to map it (the wizard, then the tester);
  • hold any button for three seconds to skip it. It still runs on the fallback map, and it is not asked about again (~/.config/sndstation/setup.json, pads_skipped). Controls maps it any time later.

A pad already in the database is never asked about.

Audio

SETTINGS → Audio sets up the unit's sound for every app (launcher/audiosetup.cpp). Everything is set and tested here once, and every app follows it: the page edits what the unit keeps (audio.json, version 3, per unit and per endpoint) and its own sound output applies it, by the same SDK functions every app opens its sound through. audio-page.md has the model and why.
Device Automatic (a USB interface when plugged in; else the headphones when in and the unit can tell; else the speaker; HDMI only when chosen), or one output: speaker, headphones, speaker + headphones where the board can, a USB interface, HDMI. Something always plays: a chosen output that goes away falls back to Automatic
Sample rate, Buffer size the playing card's, live, offering only what the device answered when asked; kept per card. The buffer size is a slider, with its length in ms
User level the playing output's system volume, a gain on the samples in software, in dB below its system levels, shared by every program (audio-levels.md)
System levels the chip's controls; its playback levels are the playing output's ceiling, kept as they move; nothing else sets it. PLAYBACK and ROUTING shown; switches, and capture and the rest, each behind a row A opens
Test sound pings peaking at full scale, at the volume (as loud as an app can play at this volume), or a steady 440 Hz at -12 dBFS
OUTPUTS one row per output this unit has; A opens it: its user level, Play on it, and for the built-in card Set up by ear and Corrections (plug detection, swap, speaker switch)
TOOLS USB interface (while one is plugged in: audio-page.md), Diagnostics, MDFourier (audio-device.md §2.4)

System levels with the test sound on plays pings at full scale (0 dBFS, past the user level; at it on headphones), over the card's playback levels: raise them until it distorts, rattles or is too loud, and back off. Each move is kept as that output's maximum, its 0 dB.

Every change is kept as it is made, into ~/.config/sndstation/audio.json, and "✓ Saved" shows in the title bar for a moment. The by-ear set-up is the exception: its answers are kept when its DONE screen says SAVE, and a run abandoned part way leaves the unit as it was. A unit nobody has set up has nothing routed: only Automatic, Built in and any other card are offered.

The page plays into the launcher's stream (launcher/audio.h), which the launcher opens when it starts and keeps: the page's test sounds join it when the page opens and fade out when it closes, and the page is the one place that reopens it (a card, a rate, a buffer size). The stream is let go of for the hand-over to an app, the screensaver and sleep (audio-stack.md).

The launcher also applies the unit's kept levels and its output's route and maximum each time it starts (audiodev::applyStartupMixer), for programs that do not open their sound through the SDK.

Vol+ and Vol- step the system volume on every launcher page but CONTROLS, which tests the keys: the volume of the output a program would play on now, 1.5 dB a press, saved at once so the next program starts there. An overlay says which output and how loud. AUDIO and the game step their own stream's, the same volume.

The detail — the survey behind the wizard, the profile schema, why the test signal holds no state: audio-device.md.

First run

After the gamepad's first run, a handheld whose unit is not set up gets a card before the list: A sets it up by ear (the wizard, then the page), B skips it. A skip is remembered for the unit (setup.json, audio_skipped); Audio sets it up any time later. A handheld is a device tree and a card with a speaker/headphone route to choose — a desktop is never asked, and its system decides where sound goes. A card with no mux but a switch named for the speaker counts too, as a two-item route, on and off, when the socket gives a signal to follow: the H616 codec in the RG40XX H reports the jack and leaves the speaker on, so that switch is its whole routing (--fake-audio h616).

MIDI

Under Settings, MIDI chooses which MIDI ports every app uses (launcher/midisettings.cpp):
MIDI in all ports, or none; a list of named ports set in system.json is kept as a third choice
MIDI out none, or all ports
MIDI controllers › pairs a BLE-MIDI keyboard or pad over Bluetooth; right or A opens Network's MIDI controllers list, B comes back here
MIDI monitor › every MIDI port, and what arrives on each input; right or A opens it, B comes back (below)

Up and down choose a row, left and right change it. Each change is saved at once into ~/.config/sndstation/system.json, only the key it changes, and apps read it when they next start.

MIDI monitor

MIDI monitor, on the MIDI page, shows the unit's MIDI devices and everything they send (sndstation/launcher/midimon.cpp, on midi.h):

  • Ports: every port midi::ports() lists, inputs and outputs, with in/out, MIDI 1.0 or 2.0, and the tier the backend is on. The list is read again when a device comes or goes: on Sink::portsChanged, or every two seconds while no input is open yet, because the backend tells only a sink that already has a port open.
  • Activity: a light for each input. It flashes on anything that arrives, whether or not the log shows it.
  • The log: newest at the bottom. Each line has the port, the channel, the message (Note On C4 vel 100, CC 20 = 73, Pitch bend +2048, Sysex 6 bytes) and its bytes in hex, from UmpToBytes. MIDI 2.0 arrives scaled to MIDI 1.0. A sysex longer than 512 bytes is logged by its size. The last 256 lines are kept.
  • Counts: messages received, hidden by the filter, and dropped. Each input's sink only copies the packet into a lock-free ring of 1024 packets, which the screen empties every frame. A burst bigger than that between two frames is dropped and counted, never waited on.

Every input is opened with midi::open() when the screen opens, and closed when it is left. The launcher's own MIDI (launcher/launchermidi.h), which listens to the unit's inputs from its start, is paused meanwhile, and the ports are the monitor's: one port has one sink. It listens again when the monitor closes. The backend is the launcher's, and stopped only when the launcher hands over to an app, sleeps or shows the screensaver: it holds no ports, and no sequencer client, while an app runs. On the sequencer tiers other programs keep their ports; on the raw MIDI tier a device has one owner, the launcher while it runs.

About

About says what the unit is and what it runs: the platform's version, the board and which physical unit it is (the SOC ID that audio.json is keyed on), the kernel, CPU, memory, uptime, SDL, the display, the input device, and the audio settings every app starts from. It is the same list an app's own ABOUT page can show, from the SDK's sysfacts::about(). Read-only; B leaves.

Screensaver

After a minute with no button pressed on the launcher's pages, the game's city goes by with no one in it (launcher/saver.*), drawing thirty frames a second. Any button brings the launcher back and does nothing else. It does not start over Controls, Audio, MIDI, Network or the game, nor while a message box is up, and a message box arriving puts it away. While it is up the launcher's sound stream is let go of, faded out and closed, so nothing holds the card; it is opened again, faded in, when the screensaver ends. Sleep does the same.

Network: Wi-Fi, Bluetooth, USB networking and SSH

Network, a row on the SETTINGS page after MIDI, puts the unit on Wi-Fi, pairs Bluetooth devices, lets a computer reach it over a USB cable, and lets it be logged in to over SSH, without taking the card out to edit files on it. A opens it; B goes back a screen, and from its menu back to SETTINGS. The row's note says how things stand: the network and address it is on, a connected Bluetooth device, USB networking's address, or, while SSH is on, SSH is ON and the command to connect with, in the warning color.

Network opens on a menu of five, each with how it stands under its name, each opening its own page:

page
Interfaces every network interface but lo, built in or a USB adapter (wlx0ccf89f495ea, enx606d3cbcf661), Wi-Fi or wired: its state and IPv4 address. To read; NetworkManager brings a wired one up by itself
Wi-Fi connected or not, the network, its IPv4 address. Choose a network, forget the one joined, Wi-Fi off or on
· networks what a scan finds, strongest first: name, WPA2 / WPA3 / open, saved, connected, signal. A joins, X scans again, Y forgets a saved one, B goes back
· passphrase the on-screen keyboard, masked: D-pad moves, A types, B deletes (B on an empty field goes back), X shift, Y space, SELECT shows or hides it, START joins. It is checked as you type: 8 to 63 characters, or 64 hex digits
Bluetooth on or off, and the paired devices, connected or not. Devices (while it is on), Bluetooth off or on
· devices what a scan of a few seconds finds, paired ones too: name, address, paired, connected. A connects (pairing first) or disconnects, X scans again, Y forgets a paired one (after a card), B goes back
· MIDI controllers the same list from an LE scan for BLE-MIDI gear alone, with the same buttons. Settings → MIDI → MIDI controllers opens this very screen, since that is where someone looking for a keyboard looks first; from there B goes back to the MIDI page, and where Bluetooth is off or absent the Bluetooth page opens instead and says so
USB networking the mode and the unit's address on it, and how to log in over it. Connected to my PC, Connected to a hub, As a host (each where the port can do it), off while one is on, and Remember network settings
SSH on or off, ssh sst@192.168.1.23 while it is on, and who could then log in. Make host keys, turn SSH on or off

Nothing is hidden for want of hardware. Every page is on every unit, and one with nothing to drive says No … device present and, where the helper can tell, why, in this order: a hardware switch (rfkill), firmware the kernel failed to load (named, from the kernel log), hardware on the SDIO bus (or a USB Bluetooth interface) with no driver bound, or no hardware at all. On these kernels a radio with no driver or no firmware is more common than no radio. A unit with no built-in Wi-Fi joins through a USB Wi-Fi adapter the same way: NetworkManager drives either.

Joining takes up to 45 seconds; a card says so, and the buttons wait. A saved network or an open one is joined without asking. A passphrase the network turns down is not kept: the keyboard comes back with it still typed, to correct. WEP and 802.1X (eduroam, company networks) are listed but not joined. Hidden networks (no name) are not listed, but the list says how many there are.

Power saving (on the Wi-Fi page) turns the radio's power saving off or on (iw, and NetworkManager's wifi.powersave for later connections), and with it the driver's deep power save where it has a switch (rtw88's disable_lps_deep, behind the "firmware failed to leave lps state" errors on an RG35XX SP). Off is kept across restarts in the helper's /etc/NetworkManager/conf.d/sndstation-wifi-powersave.conf, /etc/modprobe.d/sndstation-rtw88.conf (where rtw88 is a module) and /etc/tmpfiles.d/sndstation-rtw88.conf (where it is built in, as on the SP's kernel, so modprobe.d never applies); on removes them. A driver without the switch is said so on the row.

Bluetooth

Pairing is done with no PIN (BlueZ's NoInputNoOutput agent): a pad cannot type one back, and the devices a music unit pairs with (headphones, MIDI keyboards and controllers) do not ask for one. A paired device is trusted, so it reconnects on its own. A device that wants a PIN, or one not in pairing mode, fails to pair and the page says so.

USB networking

A network over a USB cable, with no Wi-Fi, in one of three modes. Picking one turns off whichever was on first.

  • Connected to my PC. The unit's USB port becomes a USB Ethernet device (a configfs gadget with one CDC NCM function, which Windows 10 and later, macOS and Linux drive with no extra driver; CDC ECM, which Windows cannot, on a kernel without NCM), and the unit takes 10.55.0.1/24 on it. With dnsmasq in the image, NetworkManager hands the computer an address too; without it, give the computer 10.55.0.2/24 by hand. Then ssh sst@10.55.0.1 reaches the unit, once SSH is on. The usual choice, so it is listed first.
  • Connected to a hub. The same USB Ethernet device, but the unit asks for an address rather than giving one, and keeps asking until a unit in host mode answers. Plugged into that unit, or into a hub on it, it gets a 10.56.0.x address; until then the page says it is waiting. Its MAC addresses come from the unit's machine-id, so units on one hub differ.
  • As a host. The port is a USB host, and a bridge (br-usb) takes in every USB Ethernet link on it and hands out 10.56.0.10–254, with the unit at 10.56.0.1. Units connected to a hub join it, and so does any other USB Ethernet plugged in: a USB Ethernet adapter on this unit joins the bridge rather than working on its own while host mode is on. The page says how many have joined.

No mode hands out a route or DNS: a computer or another unit reaches this one, but its own traffic never goes through it (a wired route outranks Wi-Fi, so one would take over a laptop's internet).

The device modes need a port with a device mode (a UDC under /sys/class/udc, or a USB role switch under /sys/class/usb_role that can make one) and the kernel's libcomposite. Host mode needs a host port of its own beside the UDC's, or a role switch. A mode the unit cannot do is not listed, and with none the page says what is missing. On a role switch (RK3326) the port is told to be a device in the device modes, and so is no host: a USB Wi-Fi or Ethernet adapter on that port stops working, and the page says so. Host mode on such a port refuses while another USB gadget holds it. Turning a mode off, or a failure, puts the port back as it was.

Every mode is off again at the next restart unless Remember network settings is on (it is off until turned on). Then the mode in use comes back at boot: sndstation-usbnet.service runs the helper's usb-boot, which reads /etc/sndstation/usb-network. A remembered mode the unit can no longer do is left off, and the reason goes to the journal. How it all works, and what to check when a unit does not come up: usb-networking.md.

SSH: off unless turned on here

Turning SSH on asks first, on a card with CANCEL under the cursor, saying who could then log in. It stays on through restarts until it is turned off here. The page refuses to turn it on, and says what to do instead, when:

  • the unit has no host keys yet. Release images make them on first boot; if they are missing, Make SSH host keys runs ssh-keygen -A.
  • sshd takes passwords and the user's is empty, or still the image's default (sst, which is public, or the user's own name). Exit to shell and run passwd, then turn SSH on. A key in ~/.ssh/authorized_keys does not make the default password safe while sshd still takes passwords; with PasswordAuthentication no, the key is the only way in, and that is allowed.

The page never sets a password, never adds a key and never turns SSH on by itself. Note that the sndstation release images come with openssh-server enabled by Debian's package and the login sst / sst; the page shows that as SSH is ON, and turning it off here disables it.

How it works

The launcher never runs as root. It runs one helper, /usr/lib/sndstation/sndstation-netctl (tools/sndstation-netctl), through sudo -n, and the package's install script lets the sudo group do that without a password, on a handheld only (/etc/sudoers.d/sndstation-netctl, checked with visudo, removed with the package; the same rule lets Storage mount and eject cards, below). The helper uses what the image already has:

  • Wi-Fi: NetworkManager (nmcli), which the release images ship with wpa_supplicant. A network is joined by writing a connection into NetworkManager's own store, /etc/NetworkManager/system-connections/ (0600, root), loading it and bringing it up. The passphrase reaches the helper on stdin, never on a command line (sudo logs those, and /proc shows them to everyone); it is never printed or logged, and the launcher keeps no copy. A connection that does not come up is deleted. Forgetting deletes every saved connection for that network.
  • SSH: OpenSSH's ssh.service (sshd.service elsewhere), systemctl enable --now and disable --now (its socket too). Whether the password is the default is checked as root, against /etc/shadow, with the entry's own salt.
  • Bluetooth: BlueZ's bluetoothctl (show, power, scan, pair, trust, connect, disconnect, remove). An address is checked to be one before it is passed on. BlueZ keeps the pairings, in /var/lib/bluetooth.
  • USB networking: configfs (/sys/kernel/config/usb_gadget/sndstation, after modprobe libcomposite) for the gadget, and NetworkManager connections made with save no (sndstation-usb; in host mode the bridge sndstation-usbhost and its port profile sndstation-usbhost-port), so none outlives a restart. A role switch is set to device (or host) first, and back afterward (its old role is kept in /run, with the mode in use). Remembering is /etc/sndstation/usb-network, put back at boot by sndstation-usbnet.service.
  • Interfaces: /sys/class/net, and ip -4 addr for the address, so an interface NetworkManager does not manage is listed too.
  • Why nothing is there: /sys/class/rfkill, the kernel log (dmesg) for firmware that failed to load, and /sys/bus/sdio and /sys/bus/usb for hardware with no driver bound.

Needs the image. The release images have NetworkManager and OpenSSH, but not yet BlueZ (bluez) or a USB gadget set up, and dnsmasq-base is needed for USB networking to hand out an address. Until the distribution adds them, Bluetooth says it is not installed and USB networking says what is missing; Wi-Fi and SSH work as they are.

A call that runs too long is given up on: 40 s, or 75 s for joining a network or pairing a device. The helper and anything it started are killed, and the page says the helper did not answer in time; its own calls to bluetoothctl and systemctl stop at 30 s. The status is read again every 5 s on the page and every 30 s while it is closed (for the launcher's row), without a card; a button pressed meanwhile is not held up by it, its work goes next behind its own card. That read is one helper call (status), so one sudo, which the sudo rule leaves out of the logs since it changes nothing. The helper keeps its verdict on the password (a yescrypt per candidate, slow on these CPUs) in /run, root's only, until the hash changes; Bluetooth is two bluetoothctl devices listings (BlueZ 5.65 or later), not one call per device; and USB networking's status looks for libcomposite without loading it.

It answers in lines the launcher reads (netctl 1, then key=value), so it can be tried from a shell: sudo -n /usr/lib/sndstation/sndstation-netctl wifi-status. Without the helper, on a desktop say, the page says so; with --fake-net it runs on an in-memory unit with five networks around it (correct horse joins any of them), Bluetooth off with three devices nearby, and a USB port that can do USB networking, for development and --shots (18–41, with the no-device and no-driver pages).

Storage: SD cards, USB drives and files

SETTINGS → Storage lists Home and every SD card and USB drive in the unit that is not the one the system runs from: its name (its label, or "SD card", "USB drive"), its file system, its size, and where it is mounted, with what is free on it, or that it is not mounted.

  • A opens it in the file browser, mounting it first if it is not. Every file is offered; A on one shows it as it is, the way a license is shown (an image as an image, text as text, anything else as its first bytes in hex). B goes up a folder, and from where it opened back to the list.
  • Y ejects a mounted one (written out, then unmounted: safe to take out), or mounts one that is not.
  • X lists them again: nothing polls, so a card put in while the page is open shows up on X.

The system's card has a row of its own after Home when the system can grow into what the card has unused ("System card · +25.0 GB"). An image written to a card is only as big as the image, and the rest of the card sits unused until it is grown into. The grow is the image's own /usr/local/bin/grow-rootfs (sndstation/distribution): it extends the root partition to the end of the card and grows its ext4, early in a boot, with its progress on screen, and nothing grows by itself. Without that script, or with no room, there is no row.

  • A asks first ("Grow by 25.0 GB in the next restart? Do not power off while it runs."); A again requests it (grow-rootfs request), B or any other key is a no. Then the row says it grows on the next restart, and A opens the power menu on Restart (below).
  • Y, while it is pending, cancels it (grow-rootfs cancel).

A card is mounted at /media/sndstation/<its label> (a label that is not a safe path is made one; no label, sd-mmcblk1p1), nosuid and nodev. FAT, exFAT and NTFS keep no owners, so they are mounted as the user's; the others keep their own. A card the image mounts by itself (ArkOS puts a second card at /roms2) is listed where it is, and the file browser offers it as a place. A file system it cannot mount (HFS+, say) is listed, and says so.

How it works

The listing is /usr/lib/sndstation/sndstation-storage list (tools/sndstation-storage), run as the user: lsblk needs no root. The disk the system runs from is the one any of the system's mount points (/, /boot, /flash, /storage, /userdata...) are on, and nothing on it is listed; with no such disk found, nothing is. Mounting and ejecting run the same helper through sudo -n, by the same sudo rule as Network's, and it mounts or unmounts only what it lists, and only at a new or empty directory. It answers in lines (storage 1, then vol records, a grow record for the system's card, and key=value), so it can be tried from a shell: /usr/lib/sndstation/sndstation-storage list. With --fake-storage the page runs on a made-up SD card, a USB stick and a disk it cannot read, for development and --shots (21–21g).

Software packages

SETTINGS → Software packages is everything the unit installs, through apt. Opening it asks every source first, and the page stays grey until it has compared what each has with what is installed; X asks again. Offline (as NETWORK knows it), it asks nothing, shows what is installed, and removes; nothing says up to date until every source has answered a check. Leaving it after anything was installed, removed or upgraded walks the CLAP plugin folders, as at start, and reads APPS again. Updates, whose row names the sources its updates come from, installs the unit's updates: apt-get update, then what apt upgrade does, with every update listed by where it comes from (Security, each supplemental source, the base system, Kept back), its versions, size and changelog, and apt's own progress and log while it installs. The kernel and boot loader are held; an install refuses a battery under 30% that is not charging; nothing is ever installed unasked. A background check, at most daily, lets the row say how many there are. sndstation lists the sndstation source's apps, plugins, sounds and skins to get, update (A) or remove (Y), its row saying how many are installed, how many more are available, and whether any has an update; Vendors, one row that opens the list of every instrument maker the unit has, however many there are, with their demos and free products, any of them removed from the unit with Y and added back with A, where START gets every one not installed yet, after one card, and a vendor that did not answer is in red; Install a .deb file shows a full version's .deb, from a card or a stick, and installs it (a .deb opened in Storage's files comes here too). All of it is in updates.md. With --fake-updates the page runs on made-up updates and packages (--shots 21h–21u, 21o0 the page while it asks, 21o1 and 21o2 offline, 21o3 before NETWORK has read the unit's status, 21o4 the vendors' list, 21o5 and 21o6 the page and that list with thirty vendors more).

Display

SETTINGS → Display has two rows, chosen with UP and DOWN: the screen's brightness, and the launcher's skin. Both show at once and are saved when B goes back.

Brightness

LEFT and RIGHT take the brightness down and up 5% at a time, held to keep going, and it shows at once. B goes back, and the level is saved in the platform's system.json (its user copy, "display": {"brightness"}) and set again whenever an sndstation program opens its window (the SDK's Window does it), so every app has it, started from the launcher or on its own, booted into or not. Apps have nothing to do with it: it is the unit's setting.

It drives the kernel's backlight, /sys/class/backlight/<name> (the one system.json's display.backlight names, else the kernel's preferred one), through sndstation/display.h. The level is as the eye sees it: the duty is level ^ brightness_gamma (2.2) over brightness_floor (5% of the maximum), so equal steps look equal and the lowest one still lights the screen. No root: the package's udev rule (/etc/udev/rules.d/70-sndstation-backlight.rules, handhelds only) hands the backlight's brightness to the video group, which the session's user has to be in. A unit with no backlight there (vendor sunxi kernels take it through /dev/disp) says so, and is left as it is. No brightness keys yet.

Skin

LEFT and RIGHT put on the next skin: the launcher's colors, all of them, changed from the next frame. A row of swatches shows the skin's colors. It is saved in the platform's system.json as "display": {"skin": ID} and put on when the launcher starts.

Skin
Dark the SDK's own look, and the default
Light paper and ink, for daylight; the accents darkened to keep their contrast
High contrast white on black, yellow and cyan accents, the quiet text no longer quiet
Stage red dim reds on black, for a dark stage: it keeps the eyes' night vision

The skins are config/skins.json, each a style block over the SDK's look, keyed by id. A unit's own ~/.config/sndstation/skins.json changes one or adds one without copying the rest ("order" places it; Dark stays first). A skin sets colors only: fonts and sizes would need the window opened again. An id that names no skin leaves the SDK's look on and says so.

An app wears the skin only if it asks: "skin": "system" in its manifest (above), or in its own style block.

--skin ID runs the launcher in a skin for once, without saving it. With --shots, every screen is drawn in it. The shots always include each skin on APPS and SETTINGS (22e on) and the Skin row (22d).

The on-screen keyboard

Text typed with the pad, for the Wi-Fi passphrase and anything else that needs it. It is in the library (sndstation/keyboard.h, Keyboard), so an app can use it too. Four rows of ten keys, then five wide ones: case, #+= (symbols), SPACE, DEL and an OK key the page names (JOIN on Wi-Fi). The d-pad moves and wraps on every edge, A types the key under the cursor, B deletes (and on an empty field goes back), X is shift, Y a space, START is OK from anywhere, and SELECT shows or hides a masked field. A masked keyboard overwrites its text before letting it go. The Name layout, for a short label, has capitals, digits and - + / . only.

The file browser

A file picked with the pad, for a plugin's license and anything else that needs one. It is in the library beside the keyboard (sndstation/filebrowser.h, FileBrowser), and looks and moves like it: a field saying where it is, a tile for each folder and then each file it offers, and a row of wide keys, PLACES, UP and an OK key the page names (REGISTER for a license). It starts at the places: home, anything mounted under /media, /run/media or /mnt, any FAT or exFAT volume that is not /boot, and anything mounted from a disk the system is not on, wherever the image mounts it. A page that lists the places itself (Storage) opens it in a folder instead, and up from there is back to that page. Hidden files are left out, and only files with the extensions the caller names are offered. Up and Down move, Down from the last row reaches the wide row; A opens a folder or picks a file, B goes up a folder (from the places, back), Y goes to the places, START picks the file under the cursor.

Plugins

The launcher keeps the unit's CLAP plugin cache, ~/.config/sndstation/clap_plugins.json, the one file every app reads its plugin list from (clapdb::platformDatabasePath()). Every time it starts, which is at boot and each time an app exits, once the first-run Controls and Audio are out of the way:

  1. It walks the plugin folders: plugins.scan_paths from the platform's system.json, else /usr/lib/clap, /usr/local/lib/clap, ~/.clap and every directory in $CLAP_PATH. A file whose size and modification time are what the cache last saw is not read again, so a walk that finds nothing new costs next to nothing.
  2. Each plugin that is new, or whose binary changed, is loaded in a child process and checked and rated by clapprobe at its conformant level (clap.md), at the unit's own sample rate and buffer size. A screen counts them off meanwhile. One that crashes or hangs costs a child process and a line in the cache, never the launcher. Indexing preset files is what can take long, so the first half second of it is timed: when the rate says the rest will take two seconds or more, a second bar counts the files, and B (South) stops the indexing. A quick library, and presets inside the plugin (one call, nothing to show between), show nothing. Stopped, the presets found so far are kept, the plugin is checked to the end, and the next start indexes its presets again. A library of thousands of files takes as long as it needs; only one file that takes over 10 s stops it, and its presets are then left out.
  3. If anything is new, or gone, a message box says so: each new plugin with its rating out of 100, or that it crashes, hangs or will not load and is not listed. A file of many plugins is one line: how many it holds, how many play, and their ratings (effects-pack: 12 plugins, 11 play, 71-100/100); the log has each one. A plugin whose presets were stopped says presets stopped, and one whose presets crashed or hung says presets left out. Any button closes it.

The same goes to the log (plugins: …). Twenty packaged files, 195 plugins in all, take about fourteen seconds the first time on a desktop and nothing after that.

The PLUGINS page lists every plugin the cache says plays. A on one shows it close up: its check and rating out of 100, which of the strict checks it missed, and when it was checked. There, A plays it (below), X (North) checks it again, Y (West) is its license's (REGISTER or SHOW LICENCE, when it has one), and B goes back to the list. The same buttons mean the same everywhere in the launcher: A does the thing, B goes back, X rescans or checks again, Y is the item's own second thing, START is A.

X (North) on the list walks the folders again in the same way, for a plugin installed while the launcher was up; a walk that finds nothing new shows nothing. It also asks every plugin that says what its license is what it says now (below), since a license installed or removed does not change the plugin's file; one that changed is in the message. With --no-plugin-scan it only reads the cache again.

A plugin that says what its license is (the license extension, clap.md) has a tag on the list: FREE, FOSS, DEMO, EXPIRED or REGISTERED, with DEMO and EXPIRED the ones that stand out. Its close up says the same, with the license's SPDX name and URL for one that is open source, and what the plugin tells the user for one that is not registered. A plugin that says nothing has no tag and no license rows.

  • DEMO, EXPIRED: Y (REGISTER) registers it the way it takes: a file, a key, or, when it takes both, a choice between them. A key is typed on the on-screen keyboard (B deletes, and cancels on an empty field), and START or REGISTER hands it to the plugin; a key it refuses stays there, to be corrected. A file is picked in a file browser. It starts at the places a file can come from: home, anything mounted under /media, /run/media or /mnt, and any FAT or exFAT volume that is not /boot. It offers only the files the plugin says a license ends in (all of them, when it does not say). A on a file hands it to the plugin. The plugin installs it itself, wherever it keeps its licenses, and says where. The launcher writes nothing but the plugin's new answer, into the cache. The browser is the library's (below, "The file browser"). The message after says the plugin accepted the file, and nothing of what is in it.
  • REGISTERED: a license can carry a name, an email, an address, so nothing of it is on the close up: not who it is registered to, not the file. Y (SHOW LICENCE) shows it: the file the plugin names, a PNG as the picture it is (never stretched: at the most whole times it fits, or scaled down only when it is bigger than the screen), text as text, anything else as its first 512 bytes in hex, under who it is registered to. The first time in a run it asks first, with CANCEL under the cursor. Up and Down scroll; A or B close it.

Playing a plugin

A on a plugin's close up plays it in the launcher itself: no app is started, nothing is unloaded, and B or the plugin's own quit brings back the list. The host is the platform's (ClapPlayer, clapplayer.h), and it plays into the launcher's sound stream, a source on its mixer, with the launcher's MIDI (every input the unit listens to) pointed at it: it opens no device of its own (audio-stack.md). A plugin built for the hardware gets clap.embedded-hardware (embedded-hardware.md).

  • A plugin built for the hardware (it has the extension's plugin side and asked for its event space) does its whole thing: the panel is its screen, its canvas scaled by a whole number and centered when it asks for a smaller one, and every control is its own but MENU and the volume keys, which stay the unit's. MENU opens the power menu with Close its name on top; the plugin's request_quit() closes it too. Sleep tells it (suspend(), then resume() and a RESET).
  • Any other plugin gets a test bench: the card, rate and period it plays at, its work as a share of each block (the worst in the last second), dropouts, the level of each side, MIDI in, the notes held, and a chord: A plays it while held, LEFT and RIGHT move its root a semitone, UP and DOWN an octave, Y changes its kind (major, minor, seventh, sus4). B leaves.

Its state (clap.state) is saved when it closes, however it closes (the power menu's restart, shut down and exit included), and loaded the next time it plays: ~/.local/share/sndstation/plugins/ID.state.

It runs in the launcher's process, so a plugin can take the launcher down with it. A crash ends the launcher, and the session starts it again on its main page (sndstation-session). A hang ends nothing, so a watchdog does: the main thread not back for 8 seconds, or the plugin's process() for 5 while the launcher's stream plays, ends the launcher the same way. Before loading, ~/.local/state/sndstation/plugin-running says which plugin it is, and a clean close removes it. A launcher that finds it says in the footer that the plugin stopped the last one, records when (plugins-stopped, beside it), shows that on its close up (LAST PLAYED), and plays it again only on a second A. A plugin that did not pass its check asks the same.

The power menu: sleep, restart, shut down, exit to shell

MENU (the unit's FN, Home or MENU key), or SELECT held, then START, opens the power menu on any of the launcher's pages, over whatever is showing, except CONTROLS, which tests those buttons:

Sleep
Restart
Shut down
─────────
Exit to shell

While a plugin plays (PLUGINS, A close up), Close its name is above them, the cursor on it.

Both ways work on every unit: someone used to SELECT+START on another handheld finds it, and the SDK reports that chord as MENU to every app (sndstation/pad.h, "the Menu chord"), so no app can give it another meaning. Every footer on the launcher's pages says how to reach it.

Opening it is the deliberate step, so an item acts at once, with no second question. The cursor starts on Sleep, the harmless one, so a stray A right after opening never powers anything off. B, or MENU again, closes it. While packages are installing (SETTINGS → Software packages), Restart and Shut down are dimmed and the menu says why. Restarting and shutting down say so over everything until the unit goes; refused, the launcher stays and says why. Storage's "restart now", after asking for the system's partition to grow, opens this same menu on Restart.

Shut down runs system.shutdown_cmd from the platform's system.json through sh. By default that is systemctl --no-ask-password poweroff, which logind lets the user at the unit's own screen run without root where polkit is installed, and failing that sudo -n /usr/sbin/poweroff, which the package's sudo rule (/etc/sudoers.d/sndstation-netctl, handhelds only) allows the sudo group without a password: that command, with no arguments. --no-ask-password because otherwise, where polkit says no (a session logind does not count as at the screen, such as one started from a serial console), systemctl asks for a password on the launcher's terminal and waits there, and the sudo fallback never runs. Not a bare poweroff: it lives in /usr/sbin, which an ordinary user's PATH does not have on Debian, so sh never finds it. An image without systemd names its own command there. If the command fails the launcher stays up and says so, and sudo's own words are on stderr.

Powering off is the platform's, not an app's: apps leave to the launcher (an app may offer sleep and quit, but not shut down).

The goodbye. On a handheld, every power-off (Shut down, the power button, poweroff over SSH) ends with the boot splash's dude going to bed, at the splash's size: he hops in, pulls the covers up to his chin, shuts his eyes and says さようなら in a word balloon, then the lights go out, about three and a half seconds in all. sndstation-goodbye.service, wanted by poweroff.target (so not on a restart), runs sndstation --goodbye as the session user once tty1's session has gone and the display is free. The launcher tells systemd when it has played (Type=notify, so the power-off waits that long) and keeps the screen dark to the end, so the console's shutdown messages never show.

Exit to shell ends the session (exit 87, above).

Restart (Storage's, once the system's partition is to grow) runs system.restart_cmd the same way: systemctl --no-ask-password reboot, else sudo -n /usr/sbin/reboot, which the same sudo rule allows with no arguments.

All three are in the SDK, sndstation/power.h: power::off() is SHUT DOWN's, power::restart() Storage's, and power::sleep() an app's SLEEP. Sleep runs system.sleep_cmd, which has to block until the unit wakes: by default mem written to the kernel's /sys/power/state, through sudo -n tee, which the same sudo rule allows for that one file and nothing else. The stick lights are put away before and brought back after. On a desktop without the rule it is refused, and nothing happens.
