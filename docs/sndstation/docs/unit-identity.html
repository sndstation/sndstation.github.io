Which unit this is

Part of the sndstation design. Built and shipping: include/sndstation/sysinfo.h, src/sysinfo.cpp (sysfacts::unitId(), sysfacts::socName()), shown on the launcher's ABOUT, and the key audio.json is written under.

The problem

The device tree cannot answer "which console is this". Of seventeen units surveyed, seven report the same board model and the same compatible — and they do not behave the same: five route audio cleanly, two play out of both outputs at once. A profile keyed on the DTB is shared between machines that disagree about the very thing being profiled.

The SoC can answer it

It was burned at manufacture and cannot change. RK3326 carries a package lot and a per-die block in OTP (/sys/bus/nvmem/devices/rockchip-otp0/nvmem), reverse-engineered across 18+ retail handhelds — see sndstation/src/rk3326_otp.h, which is plgDavid's work and carries its own notes.

It is a scan, in the shape the socket detection already uses on this project: try every door, report what each said, take the first that answered.

  1. The RK3326 decoder, so a family we understand yields a readable id.
  2. Then every /sys/bus/nvmem/devices/*/nvmem in turn, hashed — so a family nobody has written a decoder for (an Allwinner SID, the next clone) still produces a stable fingerprint with no new code.
SOC ID   RK3326-URKC08010-4FE23CAAD163F02F

A readable prefix and a hash of all 64 bytes. Deciding which fields matter is exactly the decision that cannot be made from a datasheet that documents none of this region, and a fingerprint ignoring the undecoded bytes cannot separate two chips differing only in them. The full hex goes into audio.json as unit_raw, beside the conclusion drawn from it, so the fingerprint can be recomputed differently later without the console.

One row on the panel, and nothing beside it

The line above the SOC ID already says "Rockchip RK3326", and the lot and the die bytes are both inside the hash — printing them as well is the same fact three times. Two consoles differ here visibly, which is the only thing a person needs from this line, and it is verbatim the key audio.json is written under, so it is also how you find this machine's entry in the file:

R40XX       RK3326-URKC08010-A599D7394C5B58B6
R36S Blue   RK3326-URKC08010-4FE23CAAD163F02F

Same lot, different unit. The decode — package, revision, die block, leakage, performance, and any non-zero byte outside those — goes to the log, and the bytes themselves to unit_raw. Neither belongs on a panel where 48 of the 64 bytes are zero on every chip seen so far.

Raspberry Pi, Amlogic, MediaTek: the chip's own number

These three families publish a serial, or a block the serial comes from, where a decoder can find it. Which family a unit is comes from the device tree's compatible, and its decoder runs after the RK3326 one and before the generic nvmem scan. The id is the chip and that number, both readable, nothing hashed when the number is already the chip's own:

Family Doors, in order Id
Raspberry Pi the firmware's system/linux,serial in the device tree (8 bytes, from OTP); the device tree's serial-number; /proc/cpuinfo Serial BCM2711-100000001A2B3C4D
Amlogic the secure monitor's chip ID (/sys/bus/platform/drivers/meson-sm/*/serial); the soc bus's serial_number; the device tree's serial-number; a vendor kernel's /proc/cpuinfo Serial S922X-0A0B0C0D0E0F101112131415
MediaTek the efuse (an nvmem device whose node is a mediatek,…efuse), hashed; LK's chosen/atag,devinfo, hashed; the soc bus's serial_number; the device tree's serial-number; androidboot.serialno on the command line MT8167-075C8ED50C0E3A03

A serial that is too short, one digit repeated or a bootloader's placeholder (0123456789ABCDEF) is refused, and the next door tried.

A MediaTek kernel has to publish the efuse for the first door to find it: CONFIG_NVMEM=y and CONFIG_NVMEM_MTK_EFUSE=y. The PlayStation Classic's device tree has its efuse (10009000.efuse), but a kernel built without those has no driver bound to it and no /sys/bus/nvmem at all, and nothing else of the chip's own either: no soc bus, no devinfo, no serial on the command line. Its log then says "no identity source", door by door.

The chip in the id is named from the device tree too: the last compatible is the SoC (mediatek,mt8167 → MT8167; Allwinner's sun50i-h700 → H700). Amlogic lists its package before the family (amlogic,s922x, amlogic,g12b → S922X, in G12B), and the kernel's soc bus, where a driver fills it in (/sys/devices/soc0/soc_id: "G12B (S922X)"), outranks the device tree. A Raspberry Pi's board revision code names its chip better than its device tree does, and is decoded into the log: revision c03114: Pi 4B 1.4, 4 GB, Sony UK, BCM2711.

ABOUT's CPU row carries the same name, "MediaTek MT8167 · 4 cores", with the soc bus's revision when there is one: a mainline arm64 kernel has no "Hardware" line in /proc/cpuinfo, and left that row saying only how many cores. After the cores come the clock the CPU runs at now and the cpufreq governor choosing it ("1.25 GHz · performance"), the fastest cluster's on a chip with two.

A unit of these families that had an id from the generic scan before has a new one now, and starts from nothing under it: what was saved under the old key is not looked for.

The log lists every door, answered or not, after a soc: line:

soc: Broadcom BCM2711 — revision c03114: Pi 4B 1.4, 4 GB, Sony UK, BCM2711
unit: BCM2711-100000001A2B3C4D  (rpi-serial)
unit:   [no ] /sys/bus/nvmem/devices/rockchip-otp0/nvmem  cannot open (root only?)
unit:   [yes] /proc/device-tree/system/linux,serial      serial 100000001a2b3c4d

tests/test_socid.cpp builds each family's /proc and /sys in a directory and scans it (sysfacts::scanUnit(root)).

This is a fingerprint, not a proof of uniqueness

Eighteen units gave one collision on the lot alone, resolved by the die bytes. That is evidence the combination discriminates better than anything else available, not that it cannot collide. Treated as one, the worst case is two consoles sharing a profile — which is where every one of them is today.

--fake-otp PATH reads the OTP from a file, so the page can be looked at and the decoder exercised on a machine with no RK3326 in it.
